# 재학습 (지속 학습, 명세 4.6)

> 코드: `recsys/retrain.py` (학습 함수는 `recsys/ume.py` 재사용), 실행: `docker compose run --rm trainer`, 테스트: `recsys/tests/test_retrain.py`

## 1. 흐름

```
서비스 DB 로그 ──▶ trainer (한 번 실행) ──▶ 새 가중치 data/models/ume/retrain_<시각>/
                       │                       └─ report.json (기준 · 새 모델 Recall@20 · MAP@12, evaluation_key)
                       ├─▶ model_versions: status="candidate" 로 등록 (채택 규칙 통과 시만)
                       └─▶ metric_snapshots: "<데이터셋>/holdout/recall@20" · "<데이터셋>/holdout/map@12" 기준 · 새 모델 한 줄씩
관리자 ──▶ 대시보드 / POST /models/{id}/activate ──▶ 운영 교체 (trainer는 교체하지 않음)
```

| 단계 | 내용 |
|---|---|
| 실행 조건 | 기준 모델(운영 중 UME)이 학습한 마지막 이벤트(`params.trained_until_event_id`, 없으면 0) 이후 비 setup **학습용 이벤트(click · add_to_cart · purchase)**가 `--min-new-logs`(기본 1만) 이상. 노출 view · 검색은 학습에 쓰지 않으므로 세지 않는다 (11-23. CT 루프는 `/metrics/log-delta?types=click,add_to_cart,purchase`로 같은 수를 본다, #70) |
| 학습 표본 | DB 이벤트 중 구매 1.0 · 장바구니 0.5 · 클릭 0.25 (조회는 정답으로 쓰지 않음). 초기 이력(setup)은 학습 이력으로는 쓰고 평가에서는 뺀다 |
| 상품 입력 | 서빙과 같은 DB 임베딩(256차원) — 학습 · 서빙 입력이 어긋나지 않는다 |
| 학습 | 기준 가중치에서 이어서 1 epoch, 학습률 1e-4 (warm start). 구조 · 나머지 설정은 기준의 config.json |
| 평가 | 최근 활동한 고객 10%의 마지막 비 setup 이벤트를 떼어(leave-last-out) 학습에 쓰지 않고, 기준 · 새 모델의 Recall@20과 MAP@12를 같은 추천 목록(텍스트 · 이미지 타워 z 합)에서 계산. MAP@12는 공통 평가 코드(`recsys/eval/metrics.py`)로 계산해 대시보드 · 모니터링 runner와 정의가 같다 |
| 채택 | 데이터셋마다 **새 MAP@12 ≥ 기준 × (1 − 0.02)** (주 지표) **그리고 새 Recall@20 ≥ 기준 × (1 − 0.10)** (보조 안전장치)면 그 데이터셋은 새 가중치, 아니면 기준 가중치 유지. 하나라도 채택되면 후보 버전 등록. 허용 범위: `--tolerance` · `--recall-tolerance` |

## 2. 실행

```bash
docker compose run --rm trainer                                                   # 기본 (1만 건 이상이면 학습 · 등록)
docker compose run --rm trainer python -m recsys.retrain --min-new-logs 0 --no-register   # 조건 무시 · 평가만
docker compose run --rm trainer python -m recsys.retrain --base 3 --tolerance 0           # 기준 버전 지정 · 엄격한 채택 (MAP@12 기준 이상)
docker compose run --rm trainer python -m recsys.retrain --no-ranker                     # 랭커는 다시 학습하지 않음 (기준 랭커 유지)
```

등록된 후보는 `GET /models`에서 `status=candidate`, `version=retrain-<시각>`으로 보인다. 교체: `POST /models/{id}/activate`.

등록된 후보는 위와 같이 확인한다. trainer는 api와 같은 이미지(`msrs-backend:latest`)를 쓰므로 api를 한 번 빌드했으면 따로 빌드하지 않는다.

### 실측 (로컬 CPU, 2026-11-11, 운영 UME v1 기준 · `--min-new-logs 0 --no-register`)

| 데이터셋 | 상품 | 이벤트 | 학습 표본 | 평가 고객 | 기준 Recall@20 | 새 Recall@20 | 학습 시간 | 채택 |
|---|---|---|---|---|---|---|---|---|
| H&M | 19,998 | 784,719 | 246,068 | 5,000 | 0.1530 | 0.1518 (−0.8%) | 10.9초 | ✅ (허용 2% 이내) |
| Amazon | 86,827 | 285,160 | 189,556 | 5,000 | 0.0198 | 0.0192 (−3.0%) | 10.1초 | ❌ 기준 유지 |

MAP@12 추가 후 같은 조건 재실행 (2026-11-16, 평가 집합 동일):

| 데이터셋 | 기준 Recall@20 | 새 Recall@20 | 기준 MAP@12 | 새 MAP@12 | 채택 (MAP@12 허용 2% · Recall@20 허용 10%) |
|---|---|---|---|---|---|
| H&M | 0.1530 | 0.1516 (−0.9%) | 0.0425 | 0.0428 (+0.9%) | ✅ |
| Amazon | 0.0198 | 0.0192 (−3.0%) | 0.0039 | 0.0041 (+5.6%) | ✅ (예전 Recall@20 단독 규칙으로는 ❌) |

- **채택 규칙을 MAP@12 하나로 통일한 이유:** 처음에는 trainer(Recall@20)와 runner(MAP@12)의 기준이 달라 Amazon에서 판정이 갈렸다. 그런데 평가 고객마다 정답이 1개라 Recall@20은 "상위 20개에 정답이 있던 고객 비율"이고, Amazon 차이는 5,000명 중 약 99명 → 96명(3명)으로 표본 오차(약 14명)의 0.2배다. MAP@12의 +5.6%도 같은 수준이다. 두 지표 모두 의미 있는 변화가 아니므로, 고객이 보는 상위 목록 품질이자 대시보드 · runner · 오프라인 결과의 공통 지표인 MAP@12를 주 지표로 두고, "기준 이상" 대신 "크게 나빠지지 않음(허용 2%)"으로 판정한다. Recall@20은 후보 범위가 크게 무너지는 경우(10% 넘게 하락)만 막는다.
- 발표 후 개선: 평가 고객 5,000 → 2만 명(오차 절반), 고정 허용 범위 대신 고객 단위 부트스트랩 구간 하한으로 판정 (`recsys/eval/stats.py`).
- 현재 DB 로그는 기준 모델이 Colab에서 이미 학습한 이력과 같아서, 새 정보가 없는 상태의 **동작 확인**이다 (기준 모델에 유리한 평가). 시뮬레이터 · 실서비스 로그가 쌓인 뒤에 의미 있는 비교가 된다.
- 채택 규칙이 데이터셋마다 따로 적용되는 것을 확인했다 (11-11 Recall@20 단독 규칙에서는 Amazon이 기준 가중치 유지).
- 전체 실행(DB 읽기 · 평가 포함)은 수 분, 학습 자체는 데이터셋 · 모달리티당 약 5초.

### 한 바퀴 리허설 (2026-11-17, main `9601b85`, 전체 카탈로그 DB)

| 단계 | 결과 |
|---|---|
| `docker compose run --rm trainer` | 새 로그 1,069,879건 → H&M · Amazon 모두 채택 (MAP@12 0.0425 → 0.0428 · 0.0039 → 0.0041), 데이터셋당 학습 약 10초 |

발표 시연 전에는 교체 후 추천을 한 번 미리 호출해 가중치를 올려 둔다. 시뮬레이터 대량 실행 로그가 쌓이면 같은 절차로 다시 돌려 숫자를 갱신한다.

## 학습형 랭커 재학습 (11-26, 다음작업 B1 후속)

기준 버전에 학습형 랭커(params `ranker`, 지금은 H&M · `v1-g1-rk`)가 있으면, trainer가 타워를 이어 학습한 뒤 **그 후보 타워로 랭커도 다시 학습**한다 (`recsys.ranker_train.retrain_ranker`). 랭커 특성(텍스트 · 이미지 점수 · 규칙 순위)이 타워 점수라서, 타워만 바꾸면 랭커가 옛 타워 기준으로 남기 때문이다. CT 루프는 그대로 `recsys.retrain`을 부르므로 따로 연결할 것이 없다.

| 단계 | 내용 |
|---|---|
| 학습 범위 | 서비스 범위 구매 (`pop_eval.service_purchases`: 비 setup, **시뮬레이터 고객 제외** — 인기 통계와 같은 범위). 쇼핑 화면 구매(A2)는 들어가고, 시뮬레이터 구매는 타워 재학습에만 쓰인다 |
| 평가 | 마지막 7일 구매를 정답으로 떼고(고객 최대 5,000명), 그 전 이력으로 새 랭커를 학습 (ranker_eval과 같은 중첩 분할). 같은 후보 300개(후보 타워의 규칙 점수)를 새 랭커 · 기준 랭커 · 규칙 순으로 매겨 MAP@12 |
| 비교 대상 | 기준 랭커. 단 기준 랭커가 평가 구간을 이미 학습에 썼으면(meta `label_end` ≥ 평가 구간 시작 — 새 구매 없이 다시 돌린 경우) 정답을 본 모델이라 **규칙과 비교**하고 보고에 `base_seen_eval_window`를 남긴다 |
| 채택 | 새 MAP@12 ≥ 비교 대상 × (1 − `--tolerance`, 기본 0.02). 통과하면 평가 구간까지 넣어 다시 학습해 `retrain_<시각>/ranker/<데이터셋>`에 저장하고 후보의 `ranker`를 그 폴더로, 아니면 기준 랭커 유지. **운영 중인 랭커 폴더는 덮어쓰지 않는다** |
| 등록 | 타워나 랭커 중 하나라도 채택되면 후보 등록. `metric_snapshots`에 `<데이터셋>/ranker/map@12` (기준 = 비교 대상 값, 후보 = 새 랭커) |
| 건너뜀 | 서비스 범위 구매가 없거나 평가 구간 고객이 50명 미만이면 `skipped` (기준 랭커 유지). 랭커 학습이 실패해도 타워 결과는 그대로 등록 (`status: failed`) |
| 끄기 | `--no-ranker` |

보고(`report.json` · stdout)에 `rankers.<데이터셋>`이 붙는다: `status` · `accepted` · `compared_with` · `rule_map@12` · `new_map@12` · `base_map@12` · `evaluation_key` · `path`. 모니터링 runner(`finish_training_report`)는 지금 `sources`(타워)만 다시 판정한다 — 랭커 판정을 runner에도 넣을지는 김광석과 정할 것.

**실측 (11-26, 전체 카탈로그 DB, 기준 `v1-g1-rk`, `--min-new-logs 0 --no-register`):** 타워 H&M MAP@12 0.0425 → 0.0426 · Amazon 0.0039 → 0.0041 (둘 다 채택). 랭커는 새 구매가 없어 기준 랭커가 평가 구간을 본 상태 → 규칙과 비교: 규칙 0.0430 · **새 랭커 0.0495** (채택) · 기준 랭커 0.0560 (정답을 본 값, 참고). 새 랭커 값은 오프라인 평가(`추천모델설계.md` "학습형 랭커", 마지막 7일 0.0497)와 같다. 랭커 재학습 43초 (타워 재학습에 더해). 새 타워 + 새 랭커로 고객 90409 상위 20개 중 8개가 기준과 겹치고, 추천 p50 58ms.

## 3. 연결 (다른 모듈)

- **모니터링 CT 루프 (광석, `monitoring/ct.py`):** `GET /metrics/log-delta`로 운영 모델의 `trained_until_event_id` 이후 새 로그 수를 보고, 1만 건 이상이면 `docker compose --profile trainer run --rm -T trainer python -m recsys.retrain --base <운영 모델 id> ...`를 실행한다. trainer도 같은 조건을 다시 확인하므로 두 번 실행돼도 안전하다.
  끝나면 출력 마지막 보고 JSON(= `report.json`)을 `monitoring.runner.finish_training_report()`로 기록한다 — 데이터셋별 `new_map@12` · `base_map@12` · `new_recall@20` · `base_recall@20` · `evaluation_key`, 채택된 데이터셋의 `text/image weights.npz` sha256, `registered_version_id`. runner도 **같은 규칙(MAP@12 × 0.98 · Recall@20 × 0.90)**으로 다시 판정해 다르면 `rule_mismatch`를 남긴다 (11-23 확정, 두 함수 일치 테스트 `monitoring/tests/test_runner.py`). 자세한 내용: `monitoring/README.md`.
- **대시보드:** `metric_snapshots`의 `<데이터셋>/holdout/map@12`(대시보드 기본 지표) · `recall@20`으로 기준 · 후보를 비교하고 교체 버튼(`activate`)을 누른다.
- **A/B:** 후보를 바로 운영하지 않고 `POST /experiments`로 기존 운영 모델과 A/B를 걸어 확인할 수도 있다.

## 4. 한계

- 1 epoch 이어서 학습이라 새 로그가 적으면 변화도 작다. 큰 변화(새 데이터셋 · 임베딩 교체)는 Colab 전체 학습(`python -m recsys.ume`)으로 한다.
- 평가는 서비스 로그 안의 다음 행동 맞히기라, 시뮬레이터 로그만 있을 때는 시뮬레이터 행동 규칙을 맞히는 정도를 본다.
- 학습 시간: 위 실측 기준 학습은 수십 초, DB 읽기 · 평가를 합쳐 수 분 (이벤트 수에 비례).
