# 로컬 페르소나 실행기 v0.1 — 김광석

## 이번에 추가한 것

기존 personas.yaml v0.2-draft를 읽는 설정 검증기, train-only 합성 고객 생성, 추천 목록의 행동 재생, 로컬 JSONL 로그와 요약 통계를 추가한다. API adapter·실제 A/B 배정·DB 쓰기는 포함하지 않는다. 기존 오프라인 지표 모듈이나 서비스 추천 모델은 변경하지 않는다.

### 발표용 설명

“기존에는 어떤 고객 성향을 시험할지만 YAML과 문서로 정했습니다. 이번에는 그 규칙을 실제로 실행해 추천 상품별 행동 로그를 만드는 로컬 프로그램을 구현했습니다. 모델 이름을 보고 클릭률을 정하지 않고, 상품과 고객 선호의 일치도로 확률을 계산합니다. 서버에 보내기 전 단계이므로 서버 A/B 성과라고 말하지 않습니다.”

## 실행 전

1. PR #23까지 병합된 main을 사용한다 (`recsys/eval/online.py` 필요).
2. 별도 작업 브랜치에서 이 PR의 파일을 적용한다. 기존 데모 data/는 유지한다.
3. Python 3.10 이상이면 simulator/README.md의 가상환경 실행을 사용한다. Mac 기본 python3가 3.9인 경우 아래 Docker 실행을 사용한다.

## Mac + 기존 Docker API 이미지 사용

터미널의 현재 폴더는 저장소 루트여야 한다. Docker Desktop이 실행 중이고 이전 데모 api 이미지가 빌드되어 있어야 한다. 동작 중인 API에 코드를 설치하지 않고, 임시 컨테이너를 한 개 실행한다.

```bash
export PATH="/Applications/Docker.app/Contents/Resources/bin:$PATH"
mkdir -p simulator/runs
docker compose run --rm --no-deps \
  -v "$PWD/simulator:/work/simulator:ro" \
  -v "$PWD/recsys:/work/recsys:ro" \
  -v "$PWD/simulator/runs:/runs" \
  -w /work api sh -c 'python -m pip install PyYAML==6.0.2 && python -m pytest -q simulator/tests && python -m simulator --data /data/dev_subset --out /runs/pilot_001'
```

PyYAML 설치에는 인터넷이 필요하다. 오류가 있으면 우회하거나 데이터 초기화하지 말고 로그를 확인한다. api 컨테이너의 기본 이미지에 numpy/pandas/pyarrow/pytest가 들어 있어 그것을 사용한다. simulator/recsys는 읽기 전용으로 연결하고 `/runs`만 출력에 쓴다. pytest 캐시 쓰기 경고가 있으면 읽기 전용 마운트 때문이며, 테스트 실패와 구분한다.

이 명령의 출력은 Mac의 `simulator/runs/pilot_001/`에 저장된다. 동일 폴더가 있으면 실패하므로 다시 실행하려면 pilot_002 등 새 이름을 사용한다. DB reset, 재적재, 모델 활성화가 필요 없다. Docker 자체의 권한·네트워크·이미지 상태는 노트북마다 다르다. Python 코드와 실제 dev_subset dry-run은 검증했지만 이 Docker 명령 전체를 이번 구현 환경에서 실행했다고 주장하지 않는다.

## 처음 결과를 읽는 순서

1. SUMMARY.md: 페르소나별 생성 고객·노출·클릭·구매. 현재 기본값은 로컬 인기 한 종류이므로 UME 개선을 말할 수 없다.
2. summary.json의 skipped_customers: train 상품 부족으로 제외한 고객. 요청 400명과 실제 생성 고객이 다르면 제외 수를 반드시 같이 적는다.
3. decisions.jsonl: 상품의 브랜드·가격·탐색·재구매 적합도, 합산 점수, 클릭 확률, 실제 난수와 행동.
4. events.jsonl: view 없이 click, click 없이 cart, cart 없이 purchase가 생기지 않았는지 확인한다.
5. manifest.json: 데이터·설정·코드 체크섬과 source별 train 날짜 창. 모델 변경 결과인지 입력·설정 변경 결과인지 구분한다.

개발 subset은 브랜드·카테고리를 제한한 작은 데이터다. 전체 서비스 분포나 전환율을 재현한 것이 아니다. 추천 후보 10개를 보기만 해도 모두 view로 기록하는 가정 역시 실제 스크롤 노출을 측정한 것이 아니다. 순위 편향·세션 내 의존성·현실 확률 보정은 구현하지 않았다.

## 다음 단계: 서버와 합의할 입력

- POST /users 및 초기 합성 이력 적재: 현재 customers.json의 ID는 DB user_id가 아니다.
- (source, processed item_id) → DB items.id 매핑. 원본 ASIN/source_item_id와도 다르다.
- 추천 요청/노출 귀속 키 및 서버 event UUID 중복 방지 계약.
- 인기/UME 모델 버전과 실험 설정을 고정하고 실제 응답 원문 수집.
- API adapter 추가 후 같은 페르소나 안에서 UME와 인기 비교. 온라인 결과와 로컬 counterfactual replay는 분리 표기.

기존 backend는 수신 시각을 created_at으로 쓴다. 이번 로컬 논리 순서를 실제 날짜로 백데이팅하여 전송하지 않는다. run_id·local_event_id가 있다는 이유만으로 서버 재전송이 안전해졌다고 판단하지 않는다.


## 리뷰 반영 — 카테고리 추출 및 Windows

- 카테고리 전체 균등 추출을 적격 카테고리의 긍정 train 구매 건수 비례 추출로 변경했다.
- 선택 규칙·확률은 manifest에 보존한다. 조건에 맞는 카테고리가 없으면 제외하고 보고한다.
- 테스트의 JSON 읽기와 설정 파일 쓰기에 UTF-8을 명시했다. Windows 직접 재실행 결과를 주장하지 않는다.
- 테스트 24개 통과. 현재 dev_subset 별도 실행에서 400명 생성·0명 제외를 확인했다. 기존 pilot_001은 덮어쓰지 않았다.
- 고객 분포가 바뀌므로 기존 실행과 CTR을 직접 성능 비교하지 않는다.
- source:processed item_id → source_item_id → DB items.id 변환, 초기 구매 이력 주입과 실험 전환의 분리는 다음 PR에서 구현한다.
