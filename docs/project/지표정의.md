# 지표 정의 (기초안 v0.1)

> 관리자 화면에 나오는 숫자와 평가 코드(`recsys/eval`)의 숫자가 같아야 한다. 이 문서는 그 공통 정의다.
> 오프라인 지표는 코드로 구현돼 있다 (`recsys/eval/metrics.py`, 테스트 `recsys/tests/test_eval.py`). 온라인 · 운영 지표는 김광석의 관리자 페이지 설계에서 확정한다.
> 실제 데이터 기준선(인기 모델) 결과: [오프라인기준선.md](오프라인기준선.md)

## 1. 오프라인 지표 (모델 실험실)

### 평가 프로토콜 (`recsys/eval/protocol.py`)

| 항목 | 정의 |
|---|---|
| 데이터 | `processed/amazon_v2`, `processed/hm`의 `events.parquet`. **데이터셋(source)마다 따로 평가** (고객 · 상품이 연결되지 않음) |
| 분할 | `split` 열 고정 분할만. H&M 마지막 7일 test · 그 전 7일 valid, Amazon 시간 순 이벤트 마지막 5% test · 그 전 5% valid |
| 학습 이력 | test 평가: train + valid (최종 성적), valid 평가: train만 (튜닝) |
| 정답 | 평가 구간 이벤트 중 `feedback ≥ 1.0` (평점 4 ~ 5점, H&M 구매)인 (고객, 상품), 중복 제거. 0.5(3점) 포함 여부는 옵션 `positive_min` |
| 평가 고객 | 정답 1개 이상 + 학습 이력 있는 고객. Amazon test 고객의 약 36%는 이력이 없어 제외 → 신규 고객은 별도 지표 |
| 후보 | 그 데이터셋의 전체 상품. 이미 산 상품도 제외하지 않음 (패션은 재구매가 있음) |
| k | 12 (상위 추천 품질, H&M 대회 기준) · 300 (후보 생성, 논문 기준) |

### 정확도 (고객별 값 → 평가 고객 평균)

| 지표 | 계산식 (정답 n개, 상위 k개) | 의미 |
|---|---|---|
| Recall@k | 상위 k 안의 정답 수 / n | 정답 중 몇 %를 찾았나 |
| HitRate@k | 상위 k 안에 정답이 하나라도 있으면 1, 아니면 0 | 한 개라도 맞힌 고객 비율 |
| NDCG@k | Σ(정답 순위 r < k) 1/log₂(r+2) ÷ Σ(j < min(n,k)) 1/log₂(j+2) | 정답을 위쪽에 놓을수록 높음 |
| MAP@k | (1/min(n,k)) × Σ(j < k) 정밀도@(j+1) × 적중_j | H&M 대회 공식 지표 |

### 다양성 · 커버리지 · 인기 편중

| 지표 | 계산식 | 의미 |
|---|---|---|
| Coverage@k | 한 번이라도 누군가의 상위 k에 나온 상품 수 / 카탈로그 상품 수 | 추천이 일부 상품에만 몰리는가 |
| BrandDiversity@k | 고객별 (상위 k의 서로 다른 브랜드 수 / k) 평균 | 한 화면에 브랜드가 얼마나 다양한가 |
| IntraListDiversity@k | 고객별 상위 k 상품 쌍의 (1 − 이미지 임베딩 코사인 유사도) 평균의 평균 | 비슷한 옷만 나오는가 (`embeddings/v2` 이미지) |
| PopularityPct@k | 상위 k 상품의 학습 기간 인기 백분위 평균 (0 = 가장 인기) | 인기 상품 위주인가 (낮을수록 인기 편중) |

### 브랜드 충성도

| 지표 | 계산식 | 의미 |
|---|---|---|
| UserBrandLoyalty (데이터) | 고객별 최다 브랜드 이벤트 수 / 전체 이벤트 수. 화면에는 중앙값과 0.5 이상 고객 비율 | 데이터 특성. Amazon 중앙값 0.17, 0.5 이상 1.3% |
| BrandAlignment@k (추천) | 고객별 상위 k 중 그 고객의 최다 브랜드 상품 비율의 평균 | 추천이 고객의 선호 브랜드를 반영하는가 |

### 구간별

정확도는 상품 구간별로도 낸다 (논문과 같은 기준): 기존(학습 판매 10회 이상) · 희소(1 ~ 9회) · 신규(평가 구간 첫 판매). — 코드 추가 예정

## 2. 온라인·관리자 화면 지표

### 시뮬레이션 보고 기준 — 페르소나 v0.2

- 1차 파일럿은 브랜드 충성형·가격 민감형·탐색형·재구매형이다. 모델 비교는 동일 페르소나 안에서 인기 모델을 기준으로 한다. 원시 CTR의 페르소나 간 차이를 모델 개선 효과로 해석하지 않는다.
- 페르소나별 CTR 상승률 = (후보 CTR − 인기 모델 CTR) / 인기 모델 CTR × 100%. 절대 차이는 (후보 CTR − 기준 CTR) × 100 %p다. 기준 0이면 상승률은 null로 표시한다. 고객·노출 수와 source 구성을 함께 기록한다.
- 페르소나별 상승률 계산과 고객 단위 신뢰구간은 아직 구현하지 않았다. A/B에서 서로 다른 고객 그룹을 무조건 짝지은 표본으로 취급하지 않는다.
- 전체 점수는 고정된 페르소나 구성의 보조 요약으로만 사용한다. 동일 비중 4종이라면 각 1/4로 고정한다는 안이며, 일부 집단이 없을 때 임의로 비중을 다시 맞추지 않고 계산 불가를 표시한다.
- 인기도 특성은 source별 train 마지막 날 기준 7일 창과 source 내 정규화를 사용한다. 이는 시뮬레이터 입력 특성의 규약이며 Recall·MAP 공식 변경이 아니다.
- 강한 브랜드 충성형의 결과에는 ‘스트레스 테스트’ 표시를 붙인다. 신상품형은 날짜 정의를 확정하기 전까지 실행하지 않는다.

### 고객별 최다 브랜드 비중 — 온라인 구현

`recsys/eval/online.py`의 `dominant_brand_share`를 사용한다. 지정 이벤트 유형(view/click/purchase)과 기간에서 고객별 max(브랜드 이벤트 수)/브랜드를 아는 전체 이벤트 수를 계산한 뒤 고객별 동일 가중 평균을 낸다. 브랜드 미상 이벤트는 제외 수를 별도로 보고하고, 유효 이벤트가 없는 고객은 제외한다. 재시도 중복 제거는 적재 단계 책임이다. 데이터 특성용 `user_brand_loyalty`의 고객별 값·중앙값과 온라인 평균을 같은 통계로 혼동하지 않는다.

이 함수는 BrandAlignment@k(추천 목록과 선호 브랜드의 일치율)와도 별개다. 반환 결과의 event_type·실제 고객/이벤트 분모를 보존한다.

## 3. 운영·데이터 집계와 갱신 규약

- 개요·A/B·작업 조회 30초, 실행 중 시뮬레이터 2초, 데이터 현황 5분은 제안값이다. 조회가 평가 재실행이나 재학습을 유발하지 않는다. 오프라인 지표는 평가 작업 완료 시만 갱신한다.
- 신규 학습 신호 수는 마지막 채택/학습 컷오프 이후 유효 이벤트를 센다. 단순 view 수와 긍정·부정 학습 신호 수를 구분한다. feedback·split은 현재 parquet에 있으며 DB Event에 자동 보존된다고 가정하지 않는다.
- 하락률은 (현재−기준)/기준×100%로 계산하며 기준 0·미수집·표본 부족은 계산 불가다. 동일 source·기간·페르소나 구성과 실제/시뮬레이션 구분을 유지한다.
- 카탈로그·브랜드·고객·이벤트 수와 누락률은 데이터 버전·source별로 계산한다. 분모와 검사 필드를 기록한다. 현재 전체 데이터 현황·품질 API가 구현돼 있다고 표시하지 않는다.
- 알림 임계값·A/B 판정·재학습·모델 교체 및 롤백 정책은 [관리자 요구사항](관리자페이지_요구사항_초안.md)의 초안으로 관리한다. 팀 승인 전 자동 실행하지 않는다.

## 4. 결과 기록·기준 구현 검증

- 평가 JSON에는 definition_version, data_version, split, cohort, relevance_rule, vector_version, 모델 버전과 K를 남긴다. 모델 ID·작성 시각 등 실제 실행 정보는 호출자가 metadata로 넣는다. 예제 값을 실험 결과로 사용하지 않는다.
- 시뮬레이션 결과에는 persona_config_version, persona, run_id, seed, source 구성, 인기 기준 모델 버전, 예상가 비중도 보존한다.
- 각 지표마다 실제 분모를 보존한다. MetricSnapshot.n 하나만으로 고객 수·카탈로그 크기·누락 건수를 모두 표현할 수 없다. 평가 작업/metadata 저장 방식을 형우와 합의한다.
- `reference.evaluate_report`는 검증 예제의 정확도·커버리지·다양성·온라인 브랜드 비중을 묶는 보조 함수이며 운영 평가 진입점이 아니다. 모델 평가는 기존 `run_eval` 결과 형식(source, model, params, eval, metrics)을 유지한다. 정확도와 목록 기반 지표의 평가 고객 분모는 다를 수 있으며 결과에서 확인 가능하다.
- 이 PR은 DB 기록·API 업로드·부트스트랩·알림 판단·재학습을 추가하지 않는다. 다른 PR의 후속 구현과 구분한다. 계산 함수와 운영 로직을 분리해 정의를 공유한다.

### 검증 예제

정답이 {A,B}, 추천이 [A,X,B]이고 K=3이면 Recall=1, AP=(1+2/3)/2=5/6이다. [A,B,X]로 순서가 좋아지면 Recall은 같지만 MAP·NDCG는 1이 된다. 테스트가 이 차이를 확인한다.

두 고객의 브랜드 비중이 각각 2/3과 1이면 평균은 5/6이다. 두 고객의 이벤트 수가 달라도 고객별 평균에 동일 가중치를 준다.

저장소 루트에서 실행:

```bash
python -m pytest -q recsys/tests
python -m unittest recsys.tests.test_reference_online -v
```

예제는 손으로 만든 가짜 데이터이며 실제 모델 점수가 아니다. 공유 데이터와 모델 가중치가 없어도 계산 정확성을 확인할 수 있다.

### 빠른 평가와 기준 구현의 역할·경계

- 모델 평가의 대표 구현은 `recsys/eval/metrics.py`, 실행은 `python -m recsys.run_eval`이다. `reference.py`는 독립 공식으로 이를 검증하는 느린 기준 구현이며 별도 운영 CLI를 두지 않는다.
- 같은 비어 있지 않은 평가 고객·중복 제거 정답·중복 없는 고정 길이 추천·카탈로그·정규화된 유효 벡터를 넣어 두 구현을 교차 검사한다. Recall·NDCG·MAP, coverage, 다양성의 결과가 일치해야 한다.
- reference는 무정답 고객을 정확도에서 제외하고 수를 반환한다. 빠른 평가에서는 build_eval_set이 사전에 유효 고객을 고르므로 같은 cohort를 전달해야 한다. 없는 추천을 0으로 채우는 reference 정책을 고정 길이 배열 평가와 묵시적으로 섞지 않는다.
- reference 다양성은 벡터를 정규화하고 누락·0·비정상 벡터를 오류 처리한다. 기존 fast 다양성은 정규화 벡터를 입력받고 0벡터 유사도를 0으로 계산하는 정책이다. 공통 유효 입력에서 일치를 검사하며 누락 처리 정책은 결과 metadata에 남긴다. 이 PR에서 기존 실험의 정책을 몰래 변경하지 않는다.
- reference의 `definition_version=0.1`은 기준 예제의 정의 버전이다. 운영 수치와 비교할 때 split·cohort·positive_min·K·벡터 버전·누락 처리 규칙까지 맞춘다. `지표정의서.md`는 삭제하고 이 문서를 공통 정의로 사용한다.
