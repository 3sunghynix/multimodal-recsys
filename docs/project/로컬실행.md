
## 4. 전체 카탈로그 (상품 106,825개)

드라이브 `msrs_project/exports/msrs_full_catalog.zip`(2.1GB): 상품 106,825 · 브랜드 19,809 · 고객 232,644 · 이벤트 1,069,873 (train 최근 기간: H&M 4주 · Amazon 8주) · 이미지 106,818장, 3단계 카테고리 열 포함.

저장소가 OneDrive 안이면 풀어 둔 이미지(약 4GB)를 OneDrive가 동기화하려고 하므로 **저장소 밖에 푼다** (예: `C:\msrs_data\full_catalog`, zip 안 `data/full_catalog/` 아래 파일들). 그리고 저장소 루트에 로컬 전용 `docker-compose.override.yml`(git 제외 — `.git/info/exclude`에 추가):

```yaml
services:
  api:
    volumes:
      - C:/msrs_data/full_catalog:/data/full_catalog
    environment:
      IMAGES_ROOT: /data/full_catalog/images
```

```bash
docker compose up -d --build db api          # 대시보드까지: docker compose up -d --build (처음 빌드는 인터넷 필요)
docker compose exec api python -m scripts.load_dev_subset --data /data/full_catalog --embeddings /data/embeddings/v2 --reset
docker compose exec api python -m scripts.register_ume --activate
```

> **재적재(`--reset`) 후 캐시:** API는 상품 색인 · 인기 점수를 메모리에 두고, 가장 큰 id 행(상품은 원본 id · 임베딩, 이벤트는 고객 · 상품 · 시각까지)으로 바뀌었는지 본다. 그래서 API를 켜 둔 채 다른 데이터로 다시 넣어도 다음 요청에서 새로 만든다. 다만 기존 상품의 임베딩만 일부 바꾼 경우처럼 마지막 행이 그대로면 감지되지 않으니, 그때는 `docker compose restart api`.

## 5. 스키마 마이그레이션 (Alembic)

지금까지 스키마를 바꿀 때마다 **`docker compose down -v` → 전체 재적재(32분)** 를 돌렸다. Alembic 도입 후 (PR #??)

### 평소 흐름
서버 시작 시 `app.db.init_db()` 가 알아서:
- **PostgreSQL**: 아래 셋 중 상황에 맞게 하나 실행
  - alembic_version 있으면 → `alembic upgrade head` (대기 중 마이그레이션 적용)
  - alembic_version 없고 items 테이블은 있음(기존 팀 DB) → `alembic stamp head` (현재 상태를 head 로 표시, 데이터 보존)
  - 둘 다 없음(완전 신규) → `alembic upgrade head` (baseline 이 테이블 생성)
- **SQLite**(테스트): 기존처럼 `Base.metadata.create_all` (빠름)

→ 수동 조치 없이 `docker compose up -d` 한 줄로 끝. **기존 데이터 보존.**

### 새로운 스키마 변경을 할 때
1. `app/models.py` 수정
2. 컨테이너 안에서:
   ```bash
   docker compose exec api alembic revision --autogenerate -m "짧은 설명"
   ```
3. 생성된 `backend/alembic/versions/XXXX_*.py` 를 열어 **검토** (autogenerate 는 pgvector 같은 특수 타입을 놓치거나 과잉 변경을 포함할 수 있음)
4. 커밋 · push. 다음 서버 재시작 때 자동 적용 (`docker compose restart api` 또는 `docker compose up -d`)

### 수동 명령 (디버깅용)
```bash
# 현재 적용된 버전
docker compose exec api alembic current

# 적용 이력
docker compose exec api alembic history

# 특정 리비전으로 되돌리기
docker compose exec api alembic downgrade -1
```

## 6. Feature Store (Redis)

명세 4.4 요구에 따라 Redis 를 사용자별 실시간 피처 저장소로 사용. docker-compose 에 추가됨 — `docker compose up -d` 한 줄로 같이 뜬다.

**저장되는 피처** (키: `u:{user_id}:...`)
- `recent_views` · `recent_clicks` — 최신 20개까지 LIST (LPUSH + LTRIM)
- `session_clicks` — 현재 세션 클릭 수 (TTL 30분, 비활동 시 자연 소멸)
- `last_activity` — 마지막 활동 시각

**쓰기:** `POST /events` 가 성공할 때마다 비동기로 반영. `is_setup=True` (초기 이력 적재) 는 Redis 에도 안 씀 (집계 제외 규칙 일관).

**읽기:** `GET /recommend/{user_id}` 응답의 `session_context.recent_clicks` 가 **Redis 우선** 으로 읽음. Redis 가 없거나 cold 이면 **DB 쿼리로 자동 폴백** — 기존 동작 그대로.

**가용성:** `REDIS_URL` 비어 있거나 Redis 다운이면 전체 **no-op**. 서버는 계속 뜨고, DB 폴백만으로 작동. 로컬 테스트(pytest)도 Redis 없이 돈다.

**측정 (명세 요구 ≤ 10ms)**
```bash
curl http://localhost:8000/features/latency
# → {"redis":true,"ping_ms":0.48,"within_spec":true,"limit_ms":10}
```
Redis 꺼지면 `{"redis":false,"reason":"..."}`.

## 7. Continuous Training 지원 (명세 4.6)

명세 4.6 "지표 모니터링 · 임계값 알림 · 재학습 트리거 · 모델 버전 관리" 중 **서버 측 뼈대**. 광석 `monitoring/runner.py` (PR #37) 가 cron 으로 호출해서 observe() 에 입력하거나, 외부 재학습 pipeline 이 결과를 저장할 때 쓴다.

**MetricSnapshot CRUD** (오프라인 평가 · 재학습 전후 비교 결과 저장)
```bash
# 저장 (재학습 pipeline 이 finish_training 후 호출)
curl -X POST http://localhost:8000/metrics/snapshots -H 'Content-Type: application/json' \
     -d '{"model_version_id":1,"metric":"recall@50","value":0.23,"n":500}'

# 조회 (대시보드가 모델별 추이 차트)
curl "http://localhost:8000/metrics/snapshots?model_version_id=1&metric=recall@50"
```

**GET /metrics/window — observe() 가 요구하는 window JSON**

광석 monitoring runner 가 cron(예: 1시간마다)으로 호출해 받은 뒤 `observe(state, window, policy)` 에 그대로 넣으면 ctr/hitrate 임계값 체크 + 재학습 트리거가 돈다.
```bash
curl "http://localhost:8000/metrics/window?start=2026-11-01T00:00:00+00:00&end=2026-11-02T00:00:00+00:00&model_version=popularity-v1&source=all"
# → {"window_id":"...","window_start":"...","window_end":"...","model_version":"popularity-v1",
#     "source":"all","cohort":"all","metric_definition_version":"v1","setup_excluded":true,
#     "views":1000,"clicks":50,"evaluated_users":100,"hit_users":20,"cumulative_new_logs":15000}
```
- 타임존 포함 ISO 8601 필수 (`+00:00` 등). 안 주면 422.
- `is_setup=True` 이벤트는 모든 집계에서 제외 (PR #30 규칙 일관).
- 데이터셋별 분리(`source=amazon/hm`)는 후속 PR — 지금은 `source=all` 만 지원.

**GET /metrics/log-delta — 재학습 트리거 판단**
```bash
curl "http://localhost:8000/metrics/log-delta?since_event_id=50000"
# → {"since_event_id":50000,"max_event_id":65000,"delta":15000}
```
runner 가 `delta >= 10000` 같은 임계값 정책(policy.json)으로 비교해 재학습 트리거. 임계값 자체는 runner 책임, 서버는 수치만 제공.
