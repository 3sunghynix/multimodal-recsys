# 개인화 추천 모델 설계 (초안 v0.1)

> 작성: 김유환 / 2026-10-29 / 상태: 팀 검토 전
> 근거: 논문(UME, `paper/msrs_paper/two_tower.py`), 기준선 [오프라인기준선.md](오프라인기준선.md), 지표 [지표정의.md](지표정의.md), 검색 [검색.md](검색.md)

## 0. 목표

- 인기 기준선보다 정확도를 올리고, 특히 **Amazon 브랜드 일치도(인기 모델 0.2%)** 를 올린다 → "브랜드 충성도 반영"의 근거.
- 서비스 조건을 만족한다: 신규 상품 · 신규 고객 처리, 재학습, A/B 동시 서빙, CPU 서버에서 빠른 응답.

## 1. 전체 구조 (3단계)

| 단계 | 하는 일 | v1 (이번) | v2 (이후) |
|---|---|---|---|
| ① 후보 생성 | 고객별 후보 300개 | **UME**: 텍스트 Two-Tower + 이미지 Two-Tower를 따로 학습, 점수 표준화 후 합 **+ γ · 인기 점수** (valid: 인기 슬롯보다 좋음 → [오프라인결과.md](오프라인결과.md)) | |
| ② 재정렬 | 후보 300 → 화면 12 | 규칙: 브랜드 선호 가산(β, Amazon 기본 2), H&M 색상 변형 묶기 | 학습형 랭커 (UME 점수 · 인기 · 가격 적합도 · 브랜드 친화도 특성) |
| ③ 실시간 | 방금 한 행동 반영 | 구조상 자동: 고객 벡터 = 최근 상품 평균이라 클릭이 바로 반영됨 | 세션 가중(최근 클릭 가중치 ↑), A/B 그룹별 밴딧 |

## 2. 모델 (① 후보 생성)

**Two-Tower (논문과 같은 구조, ID 없음)**
- 상품 타워: 상품 콘텐츠 임베딩 → MLP(512) → 128차원
- 고객 타워: 고객의 최근 긍정 상품 최대 50개의 콘텐츠 임베딩 **평균** → MLP(512) → 128차원
- 학습: 배치 내 다른 상품을 부정 예시로 쓰는 대조 학습 (temperature 0.05, lr 5e-4, batch 2048, 8 epoch — 논문 기본값)
- UME: 텍스트 전용 모델과 이미지 전용 모델을 **따로** 학습 → 고객마다 두 점수를 표준화(z)해 더함 (w = 1). 논문 3개 주에서 함께 학습(C2)보다 일관되게 좋았음 (+39% vs 텍스트 전용)

**서비스용으로 바꾸는 점**

| 항목 | 논문 | 서비스 | 이유 |
|---|---|---|---|
| 입력 임베딩 | MiniLM 384 · 이미지 768 (원본) | **embeddings/v2 PCA 256** (DB에 있는 것) | 서빙 때 DB 임베딩에 그대로 상품 타워 적용. 성능 차이는 E0에서 확인 |
| 데이터 | H&M만 | **데이터셋(source)별 모델** (Amazon, H&M) | 두 데이터셋은 고객이 연결되지 않고 임베딩 공간도 떨어져 있음 |
| 학습 표본 | 주 단위 라벨(H&M 구매) | **이벤트 단위**: 긍정 이벤트마다 (그 이전 이력 → 그 상품) | Amazon은 고객당 이벤트가 적고 시간 간격이 커서 주 단위 라벨이 거의 없음. 두 데이터셋에 같은 방식. H&M에서 주 단위와 비교(E0) |
| 평점 | 없음 (구매만) | 정답 가중치 = `feedback` (+1, 3점은 +0.5), −1은 정답 · 이력에서 제외 | 평점 C 결정. 부정 신호 학습은 v2 |
| 이력에 넣는 행동 | 구매 | 데이터셋: 긍정 이벤트, 서비스: click · add_to_cart · purchase (view 제외) | 실시간 반영(③) |

## 3. 서빙

- **산출물** (드라이브 `models/ume/{버전}/`, 서버 `/data/models/...`): 두 타워의 MLP 가중치 npz(텍스트 · 이미지 각각), `config.json`, 평가 결과 `eval.json`. 수 MB.
- **상품 벡터는 저장하지 않는다**: 서버가 시작할 때(또는 모델 교체 때) DB의 콘텐츠 임베딩에 상품 타워를 적용해 메모리에 만든다. 모델 버전마다 계산되므로 `item_vectors` 테이블이 필요 없다 (검색의 메모리 색인과 같은 방식). 신규 상품은 적재되는 순간 추천 대상.
- **추천 1건**: 고객 최근 이력 50개(events) → 평균 → 고객 타워(numpy, torch 불필요) → 그 데이터셋 상품과 내적 → 텍스트 · 이미지 점수 z 합 → 상위 300 → 재정렬 → 12.
- **신규 고객**(이력 없음): 데이터셋별 인기 (H&M 최근 7일, Amazon 전체 기간 — 기준선에서 가장 좋았던 설정). Amazon test 고객의 36%가 여기에 해당.
- **여러 데이터셋에 이력이 있는 고객**(시뮬레이터): 데이터셋별로 추천 후 검색과 같은 순위 결합(`per_source_rank`).
- **A/B**: 모델 버전마다 산출물이 따로라 두 버전을 동시에 메모리에 올려 그룹별로 서빙. 레지스트리 `ModelVersion(name="ume", params={"artifact": 경로, "beta": ...})`.

## 4. 재학습

- 콘텐츠 기반이라 **신규 상품 · 신규 고객 · 새 행동은 재학습 없이 반영**된다. 재학습은 "취향 변화에 맞춰 타워 가중치를 갱신"하는 것.
- 조건: 마지막 학습 이후 새 이벤트 수 ≥ 기준 (관리자 화면 `재학습 상태`). 기준값은 김광석 운영 지표에서.
- 실행 위치: 모델이 작아(MLP 2개 × 2) 개발 하위 집합은 서버 CPU로 가능할 것으로 예상 → E0에서 학습 시간을 재서 결정. 전체 데이터는 Colab GPU.
- 흐름: `recsys.train_ume` → 산출물 저장 → `run_eval`로 valid · test 지표 → `POST /models` 등록(candidate) → 관리자가 비교 후 교체 또는 A/B.

## 5. 실험 계획 (valid로 정하고 test는 마지막에 한 번)

| 번호 | 비교 | 결정하는 것 |
|---|---|---|
| E0 | PCA 256 vs 원본 임베딩, 이벤트 단위 vs 주 단위(H&M), 학습 시간 | 서비스 입력 · 표본 방식 · 재학습 위치 |
| E1 | 인기 · 텍스트 TT · 이미지 TT · UME (데이터셋별) | 기본 모델 (UME가 인기보다 좋은가) |
| E2 | 인기 슬롯 혼합 vs 인기 점수 가산 γ ∈ {0.5, 1, 2, 4} | ①의 인기 혼합 → **γ=2 (두 데이터셋)** |
| E3 | 브랜드 가산 β ∈ {0, 0.5, 1, 2} × γ (Amazon) | 정확도 vs BrandAlignment 교환 관계 → **β=2** |
| E4 | feedback 가중치 있음 / 없음 | 평점 반영 효과 |
| 공통 | 상품 구간별(기존 · 희소 · 신규), 다양성 · 인기 편중, 추천 1건 지연 시간 | 발표 표 |

결과는 [오프라인기준선.md](오프라인기준선.md)와 같은 형식으로 `오프라인결과.md`에 쌓는다.

## 6. 결정이 필요한 것

1. **"3단계"의 정의** — 위 표(후보 생성 → 재정렬 → 실시간)로 할지. PR 템플릿의 Two-Tower → DeepFM → MAB와 같은 흐름이고, v1은 ②를 규칙으로 둔다.
2. **재학습 자동화 범위** — 서버 CPU 자동 실행(개발 하위 집합) vs "재학습 필요" 알림 + Colab 수동 실행. E0 학습 시간 후 결정.
3. **이력에 click을 넣을지** — 넣으면 반응이 빠르지만 클릭은 구매보다 약한 신호. 시뮬레이터에서 비교 가능.
4. **브랜드 가산을 화면 옵션으로 노출할지** — 관리자 화면에서 β를 바꾸며 지표 변화를 보여 주는 데모.

## 7. 작업 순서

1. `recsys/ume.py` (학습 · 산출물 저장) + `run_eval --model ume` + 테스트 → Colab E0 · E1
2. E2 ~ E4 → 기본 설정 확정, test 한 번 → `오프라인결과.md`
3. 백엔드 `recommenders/ume.py` (numpy 서빙) + 신규 고객 대체 + 재정렬 → PR
4. 재학습 흐름 · 관리자 화면 연결 (김광석 · 김형우와)
