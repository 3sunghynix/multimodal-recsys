> 근거: 논문(UME, `paper/msrs_paper/two_tower.py`), 기준선 [오프라인기준선.md](오프라인기준선.md), 지표 [지표정의.md](지표정의.md), 검색 [검색.md](검색.md)

## 0. 목표

- 인기 기준선보다 정확도를 올리고, 특히 **Amazon 브랜드 일치도(인기 모델 0.2%)** 를 올린다 → "브랜드 충성도 반영"의 근거.
- 서비스 조건을 만족한다: 신규 상품 · 신규 고객 처리, 재학습, A/B 동시 서빙, CPU 서버에서 빠른 응답.

## 1. 전체 구조 (3단계)

| 단계 | 하는 일 | v1 (이번) | v2 (이후) |
|---|---|---|---|
| ① 후보 생성 | 고객별 후보 300개 | **UME**: 텍스트 Two-Tower + 이미지 Two-Tower를 따로 학습, 점수 표준화 후 합 **+ γ · 인기 점수** (valid: 인기 슬롯보다 좋음 → [오프라인결과.md](오프라인결과.md)) | |
| ② 재정렬 | 화면 12 | v1: **브랜드 선호 가산 β(Amazon 기본 2)는 ①과 같은 점수식에 더해 전체 상품에서 바로 상위 k를 고른다** (후보 300을 먼저 자르고 재정렬하지 않음 — 실험 · 서빙 모두 이 순서, Recall@300도 가산 후 순위 기준). 화면 단계 규칙: **H&M 색상 변형 묶기 (11-18 구현)** — 같은 `product_code`(article_id 앞 7자리)는 목록에 1개, 나머지 색상은 응답 `variant_ids` → 쇼핑 화면 "다른 색상 N개" (아래 "색상 변형 묶기") | 학습형 랭커: 후보 300 → 12 재정렬 (UME 점수 · 인기 · 가격 적합도 · 브랜드 친화도 특성) |
| ③ 실시간 | 방금 한 행동 반영 | 구조상 자동: 고객 벡터 = 최근 상품 평균이라 클릭이 바로 반영됨 | 세션 가중(최근 클릭 가중치 ↑), A/B 그룹별 밴딧 |

## 2. 모델 (① 후보 생성)

**Two-Tower (논문과 같은 구조, ID 없음)**
- 상품 타워: 상품 콘텐츠 임베딩 → MLP(512) → 128차원
- 고객 타워: 고객의 최근 긍정 상품 최대 50개의 콘텐츠 임베딩 **평균** → MLP(512) → 128차원
- 학습: 배치 내 다른 상품을 부정 예시로 쓰는 대조 학습 (temperature 0.05, lr 5e-4, batch 2048, 8 epoch — 논문 기본값)
- UME: 텍스트 전용 모델과 이미지 전용 모델을 **따로** 학습 → 고객마다 두 점수를 표준화(z)해 더함 (w = 1). 논문 3개 주에서 함께 학습(C2)보다 일관되게 좋았음 (+39% vs 텍스트 전용)

**서비스용으로 바꾸는 점**

| 항목 | 논문 | 서비스 | 이유 |
|---|---|---|---|
| 입력 임베딩 | MiniLM 384 · 이미지 768 (원본) | **embeddings/v2 PCA 256** (DB에 있는 것) | 서빙 때 DB 임베딩에 그대로 상품 타워 적용. 성능 차이는 E0에서 확인 |
| 데이터 | H&M만 | **데이터셋(source)별 모델** (Amazon, H&M) | 두 데이터셋은 고객이 연결되지 않고 임베딩 공간도 떨어져 있음 |
| 학습 표본 | 주 단위 라벨(H&M 구매) | **이벤트 단위**: 긍정 이벤트마다 (그 이전 이력 → 그 상품) | Amazon은 고객당 이벤트가 적고 시간 간격이 커서 주 단위 라벨이 거의 없음. 두 데이터셋에 같은 방식. H&M에서 주 단위와 비교(E0) |
| 평점 | 없음 (구매만) | 정답 가중치 = `feedback` (+1, 3점은 +0.5), −1은 정답 · 이력에서 제외 | 평점 C 결정. 부정 신호 학습은 v2 |
| 이력에 넣는 행동 | 구매 | 데이터셋: 긍정 이벤트, 서비스: click · add_to_cart · purchase (view 제외) | 실시간 반영(③) |

## 3. 서빙

- **산출물** (드라이브 `models/ume/{버전}/`, 서버 `/data/models/...`): 두 타워의 MLP 가중치 npz(텍스트 · 이미지 각각), `config.json`, 평가 결과 `eval.json`. 수 MB.
- **상품 벡터는 저장하지 않는다**: 서버가 시작할 때(또는 모델 교체 때) DB의 콘텐츠 임베딩에 상품 타워를 적용해 메모리에 만든다. 모델 버전마다 계산되므로 `item_vectors` 테이블이 필요 없다 (검색의 메모리 색인과 같은 방식). 신규 상품은 적재되는 순간 추천 대상.
- **추천 1건**: 고객 최근 이력 50개(events) → 평균 → 고객 타워(numpy, torch 불필요) → 그 데이터셋 상품과 내적 → 텍스트 · 이미지 점수 z 합 + γ · 인기 점수 + β · [선호 브랜드] → 상위 k (전체 상품 기준). 선호 브랜드는 긍정 이력의 최다 브랜드.
- **신규 고객**(이력 없음): 데이터셋별 인기 (H&M 최근 7일, Amazon 전체 기간 — 기준선에서 가장 좋았던 설정). Amazon test 고객의 36%가 여기에 해당.
- **여러 데이터셋에 이력이 있는 고객**(시뮬레이터): 데이터셋별로 추천 후 검색과 같은 순위 결합(`per_source_rank`).
- **A/B**: 모델 버전마다 산출물이 따로라 두 버전을 동시에 메모리에 올려 그룹별로 서빙. 레지스트리 `ModelVersion(name="ume", params={"artifact": 경로, "beta": ...})`.

## 4. 재학습

- 콘텐츠 기반이라 **신규 상품 · 신규 고객 · 새 행동은 재학습 없이 반영**된다. 재학습은 "취향 변화에 맞춰 타워 가중치를 갱신"하는 것.
- 조건: 마지막 학습 이후 새 이벤트 수 ≥ 기준 (관리자 화면 `재학습 상태`). 기준값은 김광석 운영 지표에서.
- 실행 위치: 모델이 작아(MLP 2개 × 2) 개발 하위 집합은 서버 CPU로 가능할 것으로 예상 → E0에서 학습 시간을 재서 결정. 전체 데이터는 Colab GPU.
- 흐름: `recsys.train_ume` → 산출물 저장 → `run_eval`로 valid · test 지표 → `POST /models` 등록(candidate) → 관리자가 비교 후 교체 또는 A/B.

## 5. 실험 계획 (valid로 정하고 test는 마지막에 한 번)

| 번호 | 비교 | 결정하는 것 |
|---|---|---|
| E0 | PCA 256 vs 원본 임베딩, 이벤트 단위 vs 주 단위(H&M), 학습 시간 | 서비스 입력 · 표본 방식 · 재학습 위치 |
| E1 | 인기 · 텍스트 TT · 이미지 TT · UME (데이터셋별) | 기본 모델 (UME가 인기보다 좋은가) |
| E2 | 인기 슬롯 혼합 vs 인기 점수 가산 γ ∈ {0.5, 1, 2, 4} | ①의 인기 혼합 → γ=2 (두 데이터셋, valid) → **11-23 운영값 γ=1** (아래 "인기 보정 γ 재확인") |
| E3 | 브랜드 가산 β ∈ {0, 0.5, 1, 2} × γ (Amazon) | 정확도 vs BrandAlignment 교환 관계 → **β=2** |
| E4 | feedback 가중치 있음 / 없음 | 평점 반영 효과 |
| 공통 | 상품 구간별(기존 · 희소 · 신규), 다양성 · 인기 편중, 추천 1건 지연 시간 | 발표 표 |

결과는 [오프라인기준선.md](오프라인기준선.md)와 같은 형식으로 `오프라인결과.md`에 쌓는다.

## 6. 결정이 필요한 것

1. **"3단계"의 정의** — 위 표(후보 생성 → 재정렬 → 실시간)로 할지. PR 템플릿의 Two-Tower → DeepFM → MAB와 같은 흐름이고, v1은 ②를 규칙으로 둔다.
2. **재학습 자동화 범위** — 서버 CPU 자동 실행(개발 하위 집합) vs "재학습 필요" 알림 + Colab 수동 실행. E0 학습 시간 후 결정.
3. **이력에 click을 넣을지** — 넣으면 반응이 빠르지만 클릭은 구매보다 약한 신호. 시뮬레이터에서 비교 가능.
4. **브랜드 가산을 화면 옵션으로 노출할지** — 관리자 화면에서 β를 바꾸며 지표 변화를 보여 주는 데모.

## 7. 작업 순서

1. `recsys/ume.py` (학습 · 산출물 저장) + `run_eval --model ume` + 테스트 → Colab E0 · E1
2. E2 ~ E4 → 기본 설정 확정, test 한 번 → `오프라인결과.md`
3. 백엔드 `recommenders/ume.py` (numpy 서빙) + 신규 고객 대체 + 재정렬 → PR
4. 재학습 흐름 · 관리자 화면 연결 (김광석 · 김형우와)

## 색상 변형 묶기 (11-18, 다음작업 C1)

H&M 추천 12개 중 평균 4.6개가 같은 옷의 색상 변형이었다 (화면의 38%). 같은 `product_code`는 목록에 한 번만 보여 주고, 나머지 색상은 `recommendations[].variant_ids`로 돌려준다. UME 재정렬(`services/rerank.py` `max_per_variant`, 기본 1)과 인기 목록(신규 고객 · 인기 모델) 모두 적용. Amazon은 변형 정보가 없어 묶지 않는다.

영향 (전체 카탈로그 서비스 로그 leave-last-out, H&M 평가 고객 5,000명, 운영 가중치, UME 순위에 묶기만 적용):

| 같은 옷 허용 | 정확 일치 MAP@12 | 정확 일치 Recall@12 | 같은 옷 맞힘 Recall@12 | 목록당 중복 |
|---|---|---|---|---|
| 제한 없음 (이전) | 0.0425 | 0.118 | 0.162 | 4.6 |
| **1개 (채택)** | 0.0340 (−20%) | 0.079 | **0.198 (+22%)** | 0 |
| 2개 | 0.0391 (−8%) | 0.098 | 0.177 | 2.9 |
| 3개 | 0.0407 (−4%) | 0.105 | 0.171 | 3.7 |

정확 일치 지표는 같은 옷의 여러 색을 함께 보여 줄수록 유리하다 (정답 색이 목록에 있을 확률). 서비스는 색상을 `variant_ids`로 고를 수 있으므로 "같은 옷을 맞혔는가"를 기준으로 1개를 택했다. 오프라인 실험 · 논문 · trainer 채택 판정의 MAP@12는 묶기 전 모델 순위 그대로라 바뀌지 않는다. 서비스 지표를 보고할 때는 코드 단위 지표를 함께 적는다.

## 인기 보정 γ 재확인 (11-23, 다음작업 C2)

오프라인(Kaggle 분할 valid)에서 고른 γ = 2를 서비스 DB 구매 로그로 다시 쟀다. 운영 가중치(`{source}_test_pca`), 서비스와 같은 인기 정의(구매만, H&M 최근 7일 · Amazon 전체, log1p 표준화), Amazon은 β = 2 포함. 재정렬 · 색상 묶기 없이 점수 순위만. 평가 고객 데이터셋마다 5,000명 (무작위, seed 42). 재현: `docker compose --profile trainer run --rm trainer python -m recsys.pop_eval`

| 데이터셋 · 분할 | γ | MAP@12 | Recall@12 | Coverage@12 | 목록 중 상위 1% 인기 상품 |
|---|---|---|---|---|---|
| H&M · 마지막 구매 (trainer 분할) | 0 | 0.0401 | 0.118 | 0.596 | 9% |
| | 1 | **0.0595** | **0.169** | 0.327 | 37% |
| | 2 (운영) | 0.0562 | 0.150 | 0.176 | 64% |
| | 4 | 0.0365 | 0.096 | 0.054 | 92% |
| H&M · 마지막 7일 (Kaggle 방식) | 0 | 0.0326 | 0.064 | 0.683 | 6% |
| | 1 | **0.0404** | **0.083** | 0.385 | 28% |
| | 2 (운영) | 0.0374 | 0.080 | 0.209 | 56% |
| Amazon · 마지막 구매 | 0 | 0.0033 | 0.013 | 0.359 | 4% |
| | 1 | 0.0077 | **0.024** | 0.146 | 50% |
| | 2 (운영) | **0.0087** | 0.022 | 0.049 | 88% |
| Amazon · 마지막 7일 | 1 | 0.0072 | **0.019** | 0.148 | 49% |
| | 2 (운영) | **0.0078** | 0.018 | 0.049 | 88% |

γ = 1 − γ = 2 (고객 단위 paired bootstrap 95% 구간):

| | MAP@12 | Recall@12 |
|---|---|---|
| H&M · 마지막 구매 | +0.0034 [+0.0004, +0.0063] (+6%) | +0.019 [+0.013, +0.026] (+13%) |
| H&M · 마지막 7일 | +0.0030 [+0.0013, +0.0048] (+8%) | +0.003 [−0.001, +0.006] |
| Amazon · 마지막 구매 | −0.0010 [−0.0028, +0.0008] | +0.002 [−0.001, +0.006] |
| Amazon · 마지막 7일 | −0.0006 [−0.0020, +0.0008] | +0.001 [−0.002, +0.004] |

- 인기 보정 자체는 두 데이터셋 · 두 분할 모두 효과가 크다 (γ = 0 대비).
- **H&M은 γ = 1이 γ = 2보다 정확도도 높고** (두 분할 모두 MAP 구간 > 0) 추천되는 상품 종류가 약 2배다.
- **Amazon은 γ = 1과 2의 정확도 차이가 유의하지 않고**, γ = 2에서는 목록의 88%가 상위 1% 인기 상품이다 (Coverage 0.049). γ = 1이면 50% · Coverage 3배.
- 그래서 **두 데이터셋 모두 γ = 1로 바꿨다** (11-23, `ume.DEFAULTS` · `register_ume.py` 기본값, 운영 모델은 새 버전으로 등록 → 아래). 오프라인 γ = 2는 Kaggle 분할 valid에서 MAP@12만 보고 고른 값이고, 서비스 DB(시험 기간 구매)에서는 1이 더 낫거나 같다.
- 참고: 11-18 `variant_eval` 첫 실행의 "γ = 2에서 MAP 0.0161"은 평가 버그였다. 인기 창을 전체 이벤트 마지막 시각으로 잡았는데, DB의 시연 클릭 20건이 2026-11 시각이라 창이 시연 클릭만 담았다. 서비스(`_popularity_z`)는 비 setup 구매 기준이라 영향 없다. 이 표의 γ = 0 값은 구매만 · 무작위 고객이라 `variant_eval`의 "제한 없음"(0.0425)과 직접 비교하지 않는다.

운영 모델 바꾸기 (각자 DB에서 한 번): 전체 카탈로그 기준

```bash
docker compose run --rm api python -m scripts.register_ume --version v1-g1 --gamma 1.0 --activate
```

되돌리기: 대시보드 › 모니터링 › 모델 버전에서 이전 버전(γ = 2)을 다시 운영으로 지정.

## 재구매 정책 (11-23, 다음작업 C3)

이미 산 상품을 추천 후보에서 뺄지 남길지를 서비스 DB 구매 로그로 쟀다. 조건은 위 "인기 보정 γ 재확인"과 같다 (운영 가중치, γ = 1, Amazon β = 2, 재정렬 없음, 데이터셋마다 고객 5,000명). 재현: `docker compose --profile trainer run --rm trainer python -m recsys.repurchase_eval`

정책: **그대로**(지금까지 서비스) · **제외**(학습 구간에 산 상품 전부 뺌) · **최근 30일 제외**(학습 구간 마지막 구매 기준 30일 안에 산 것만 뺌). H&M 서비스 로그는 29일치라 "최근 30일 제외"가 "제외"와 같다.

- **H&M은 남긴다.** 정답의 5 ~ 7%가 재구매이고, 모델이 이미 산 상품을 상위에 올려 그 재구매를 맞힌다. 빼면 Kaggle 방식(마지막 7일)에서 MAP가 절반 아래로 떨어진다. 마지막 구매 분할은 MAP 차이가 유의하지 않고 Recall은 떨어진다.
- **Amazon은 뺀다.** 서비스 로그 28.5만 건 중 같은 고객이 같은 상품을 두 번 산 경우가 한 번도 없다 (리뷰 기반 로그라 고객 · 상품당 한 건). 그래서 이미 산 상품이 차지한 자리는 늘 빗나가고, 빼면 MAP가 22 ~ 24% 오른다. 다만 이 개선은 데이터 성질에서 바로 나오는 것이라 "재구매를 안 한다"는 근거로는 약하다. 실제 서비스라면 티셔츠 · 양말 같은 기본템은 재구매가 있을 수 있다 — 시뮬레이터의 실용주의자 페르소나(재구매 0.5)가 이 가정이므로, 시뮬레이터 A/B에서는 Amazon 제외가 실용주의자 CTR을 낮출 수 있다.
- "최근 30일 제외"는 Amazon에서 "제외"보다 약간 낮다 (산 지 오래된 상품도 다시 맞을 일이 없으므로).

**적용 (11-23):** `ume.DEFAULTS["exclude_purchased"] = {"amazon": True}`, `register_ume.py`도 같은 값을 적는다. 제외는 점수 계산 뒤 후보에서 빼는 방식이라 표준화 · 인기 캐시 · 재정렬 빈 자리 채우기에 그대로 맞물린다 (재정렬이 산 상품을 다시 넣지 않음). 기존 운영 모델(`v1-g1` 등)은 params에 이 키가 없어 기본값이 적용되므로 **다시 등록할 필요 없다** — 끄려면 params에 `"exclude_purchased": {}`. 전체 카탈로그 DB 확인: 구매 5건 이상 고객 200명씩, 상위 20개 중 이미 산 상품 Amazon 1.69개 → 0개, H&M 2.41개 그대로, 추천 시간 p50 Amazon 38ms · H&M 22ms.

## 최근성 반영 (11-23, 다음작업 C4)

고객 타워 입력(최근 50개 이력 임베딩의 단순 평균)을 최근 행동일수록 크게 가중한 평균으로 바꿔 봤다. 모델은 다시 학습하지 않고 입력 평균만 바꾼다. 조건은 "재구매 정책"과 같다 (운영 가중치, γ = 1, Amazon β = 2, Amazon 산 상품 제외, 재정렬 없음, 데이터셋마다 고객 5,000명). 평가 코드의 단순 평균이 학습 · 서빙 코드(`tower_vectors`)와 같은 벡터를 내는지 확인했다. 재현: `docker compose --profile trainer run --rm trainer python -m recsys.recency_eval`

가중: **순위 λ** = 가장 최근부터 λ^0, λ^1, … / **시간 h일** = 0.5^(고객 마지막 이력과의 경과일 / h). 평균 이력 길이는 H&M 5 ~ 7개, Amazon 6 ~ 7개.

MAP@12 차이 (가중 − 단순 평균, paired bootstrap 95% 구간):

| 가중 | H&M · 마지막 구매 | H&M · 마지막 7일 | Amazon · 마지막 구매 | Amazon · 마지막 7일 |
|---|---|---|---|---|
| 단순 평균 (기준 MAP) | 0.0595 | 0.0404 | 0.0095 | 0.0087 |
| 순위 0.9 | **+0.0043 [+0.0025, +0.0061] (+7%)** | **+0.0017 [+0.0005, +0.0030] (+4%)** | +0.0001 [−0.0004, +0.0005] | −0.0000 [−0.0004, +0.0004] |
| 순위 0.8 | +0.0071 [+0.0044, +0.0099] (+12%) | +0.0012 [−0.0009, +0.0031] | −0.0004 [−0.0013, +0.0005] | −0.0001 [−0.0006, +0.0004] |
| 순위 0.7 | +0.0071 [+0.0036, +0.0106] (+12%) | +0.0006 [−0.0020, +0.0030] | −0.0008 [−0.0020, +0.0004] | −0.0005 [−0.0013, +0.0004] |
| 시간 7일 | +0.0093 [+0.0068, +0.0119] (+16%) | +0.0024 [+0.0011, +0.0037] (+6%) | −0.0010 [−0.0023, +0.0002] | −0.0006 [−0.0016, +0.0004] |
| 시간 30일 | +0.0038 [+0.0025, +0.0050] (+6%) | +0.0013 [+0.0008, +0.0020] (+3%) | −0.0001 [−0.0007, +0.0004] | +0.0001 [−0.0005, +0.0007] |
| 시간 90일 | +0.0011 [+0.0005, +0.0018] (+2%) | +0.0003 [+0.0000, +0.0007] | +0.0002 [−0.0001, +0.0006] | +0.0001 [−0.0001, +0.0004] |

- **H&M은 최근성이 확실히 도움이 된다.** 오프라인 1위는 시간 7일 (두 분할 모두 구간 > 0).
- **Amazon은 어떤 가중도 차이가 유의하지 않다** → 단순 평균 유지.
- **서빙은 H&M 순위 λ = 0.9로 정했다** (두 분할 모두 구간 > 0, +7% · +4%). 시간 감쇠를 쓰지 않은 이유: 서비스 DB에는 데이터셋 이력(2020년 등)과 화면 · 시뮬레이터 행동(2026년)이 섞여 있다. 데이터셋 고객이 오늘 한 번 클릭하면 시간 7일 가중에서는 과거 이력 가중이 0.5^(2,000일 / 7) ≈ 0이 되어 고객 벡터가 그 클릭 하나로 바뀐다 (세션 반영 0.3과도 겹친다). 순위 감쇠는 시각 차이와 무관하게 새 행동 하나를 이력 한 칸만큼만 더 무겁게 본다. 실제 사용 로그가 주 이력이 되면 시간 감쇠를 다시 볼 만하다.
- 여러 가중 중 가장 좋은 것을 같은 데이터에서 골랐으므로 차이는 약간 낙관적이다. λ = 0.9는 1위가 아니라 두 분할 모두 유의한 것 중 가장 보수적인 값이라 이 영향이 작다.

**적용 (11-23):** `ume.DEFAULTS["recency_decay"] = {"hm": 0.9}`, `register_ume.py`도 같은 값을 적는다. 기존 운영 모델(`v1-g1` 등)은 params에 이 키가 없어 기본값이 적용된다 — **다시 등록할 필요 없다.** 끄려면 params에 `"recency_decay": {}`. 전체 카탈로그 DB 확인 (구매 5건 이상 고객 200명씩): H&M 상위 20개 중 76%가 단순 평균과 같고 24%가 바뀜, Amazon 100% 그대로. 추천 시간 p50 H&M 22ms · Amazon 34ms.

## 학습형 랭커 (11-24, 다음작업 B1 — 오프라인 단계)

명세의 2단계(후보 생성 → 랭킹)를 학습으로 바꾸면 나아지는지 쟀다. 지금 규칙 점수(z(text) + z(image) + γ · 인기 z [+ β · 선호 브랜드], C3 · C4 반영) 상위 **300개를 후보**로 두고, GBDT(scikit-learn `HistGradientBoostingClassifier`, 새 의존성 없음)가 다시 순위를 매긴다. LightGBM은 로컬 PyPI 접속이 막혀(백신 SSL 검사) 쓰지 않았다. 재현: `docker compose --profile trainer run --rm trainer python -m recsys.ranker_eval` (trainer 이미지가 #65 이전이면 `-v ./backend/app:/app/app:ro`를 붙이거나 `docker compose build`)

- **학습 데이터에 평가 구간이 들어가지 않는다:** 평가 구간 전 이력을 같은 분할 방식으로 한 번 더 나눠, 그 안의 이력으로 후보 · 특성을 만들고 그 안의 정답 구간으로 라벨을 단다. 고객 5,000명, 양성 전부 + 고객당 음성 50개.
- **특성 11개:** 텍스트 · 이미지 점수, 규칙 순위, 인기 z, 브랜드 일치, 같은 상품 구매 수 · 경과일, 같은 옷 다른 색 구매, 이력 중 같은 소분류 비율, 가격 차(log), 이력 수. 데이터셋에서 값이 하나뿐인 특성은 뺀다 (H&M 브랜드 일치, Amazon 구매 특성 3개).

| 데이터셋 · 분할 | 후보 300개 재현율 | 규칙 MAP@12 | 랭커 MAP@12 | 랭커 − 규칙 MAP (95% 구간) | Recall@12 |
|---|---|---|---|---|---|
| H&M · 마지막 구매 | 53% | 0.0638 | **0.0866** | **+0.0228 [+0.0182, +0.0274] (+36%)** | 0.177 → 0.207 (+17%) |
| H&M · 마지막 7일 | 30% | 0.0421 | **0.0497** | **+0.0076 [+0.0050, +0.0102] (+18%)** | 0.085 → 0.100 (+19%) |
| Amazon · 마지막 구매 | 14% | 0.0095 | 0.0092 | −0.0003 [−0.0016, +0.0013] | 0.026 → 0.022 (−17%, 유의) |
| Amazon · 마지막 7일 | 11% | 0.0087 | 0.0083 | −0.0004 [−0.0017, +0.0010] | 차이 없음 |

규칙 MAP는 C4 평가의 λ = 0.9 값과 같다 (같은 점수 · 같은 고객).

- **H&M은 크게 오른다** (두 분할 모두 구간 > 0). 중요한 특성(permutation, 검증 AUC 감소): 규칙 순위 · 인기 z · **같은 옷 다른 색을 산 적 있음** · 이력 수 순. 규칙 점수가 이미 좋은 출발점이고, 인기와 "산 옷의 다른 색"을 상품마다 다르게 쓰는 것을 랭커가 배운다 (규칙은 γ 하나로 모두에게 같게 더함).
- **Amazon은 오르지 않는다.** 양성 표본이 800 ~ 1,300개뿐이고 후보 재현율도 11 ~ 14%라 배울 것이 적다. Amazon은 규칙 점수 유지.
- 후보 재현율이 상한이다 (H&M 마지막 7일은 정답의 30%만 후보 안). 후보를 늘리거나 후보 경로를 추가(재구매 · 같은 옷 다른 색)하면 더 오를 여지가 있다.

**서빙 (11-24, H&M만):** 아래 "학습형 랭커 서빙" 절.

## 학습형 랭커 서빙 (11-24, 다음작업 B1)

위 "학습형 랭커"의 결과대로 **H&M만** 규칙 점수 상위 300개를 랭커 확률 순으로 다시 매긴다. Amazon은 규칙 그대로.

- **특성 코드는 한 곳:** `backend/app/services/ranker.py`의 `candidate_features`를 평가(`recsys/ranker_eval.py`) · 학습(`recsys/ranker_train.py`) · 서빙(`recommenders/ume.py`)이 함께 쓴다. 평가를 이 함수로 바꾼 뒤에도 위 표의 수치가 소수점까지 같았다.
- **기준 시각:** 경과일 특성은 그 데이터셋 서비스 구매의 마지막 시각 기준 (인기 창과 같은 값, `_popularity_z` 캐시). 학습 때와 같다.
- **켜고 끄기:** 모델 버전 params `ranker: {"hm": "/data/models/ranker/hm"}`. 기본값이 아니라 **새 버전으로 등록**해서 켠다 (C3 · C4와 달리 버전 id가 바뀌어 지표에서 구분된다). 폴더가 없거나 파일이 이상하면 그 데이터셋은 규칙 점수로 돌아간다 (오류 없음). 응답 `score_basis`는 `ranker_probability`.
- **응답 시간:** GBDT 예측은 한 스레드로 한다 (OpenMP 스레드가 torch 스레드 풀과 부딪혀 요청 안에서 63ms → 한 스레드 8ms). 전체 카탈로그 DB, 구매 5건 이상 고객 200명: H&M p50 24 → 43ms · p95 64 → 111ms, Amazon 그대로.
- **추천 변화:** H&M 상위 20개 중 40%가 바뀐다 (Amazon 0%).

```bash
# 1) 학습 (서비스 구매 로그 전체, 마지막 7일 라벨 · 약 2분) → data/models/ranker/hm/{model.joblib, meta.json}
docker compose --profile trainer run --rm trainer python -m recsys.ranker_train
# 2) 랭커를 켠 버전 등록 (후보로만, 확인 후 대시보드에서 교체) — --activate를 붙이면 바로 운영
docker compose run --rm api python -m scripts.register_ume --version v1-g1-rk --ranker-root /data/models/ranker
```

되돌리기: 대시보드 › 모니터링 › 모델 버전에서 `v1-g1`을 다시 운영으로.

## 비교 모델 (11-26, 다음작업 B2)

명세의 "비교 모델 3 ~ 4개"에 맞춰 인기 · **ItemKNN** · UME(지금 서비스 규칙) · 학습형 랭커를 같은 조건에서 비교했다. 서비스 범위 구매 로그, C2 ~ B1과 같은 두 분할 · 고객 5,000명, 모든 모델에 서비스와 같은 재구매 정책(Amazon만 산 상품 제외), 재정렬 없음. 재현: `docker compose --profile trainer run --rm trainer python -m recsys.baselines_eval` (랭커는 `recsys.ranker_eval`)

- **ItemKNN** (아이템 기반 협업 필터링, Sarwar et al., 2001): 점수(u, i) = Σ_{j ∈ u가 산 상품} co(j, i) / √(n_j · n_i). co = 두 상품을 모두 산 고객 수, n = 산 고객 수. 이웃이 없으면 인기 순. 콘텐츠(텍스트 · 이미지)를 쓰지 않는 순수 행동 기반 기준선이다.

| 모델 | H&M 마지막 구매 | H&M 마지막 7일 | Amazon 마지막 구매 | Amazon 마지막 7일 |
|---|---|---|---|---|
| 인기 | 0.0061 | 0.0076 | 0.0053 | 0.0057 |
| ItemKNN | 0.0511 | 0.0391 | 0.0011 | 0.0012 |
| UME 규칙 (서비스 `v1-g1`) | 0.0638 | 0.0421 | **0.0101** | **0.0087** |
| 학습형 랭커 (H&M `v1-g1-rk`, #77) | **0.0866** | **0.0497** | — | — |

MAP@12. ItemKNN − UME 규칙 (95% 구간): H&M −0.0127 [−0.0173, −0.0082] (−20%) · −0.0031 [−0.0060, −0.0001] (−7%), Amazon −0.0091 [−0.0116, −0.0070] (−90%) · −0.0075 [−0.0095, −0.0058] (−86%).

| Coverage@12 (추천된 서로 다른 상품 / 카탈로그) | H&M 마지막 구매 | H&M 마지막 7일 | Amazon 마지막 구매 | Amazon 마지막 7일 |
|---|---|---|---|---|
| ItemKNN | **0.70** | **0.75** | **0.29** | **0.28** |
| UME 규칙 | 0.33 | 0.39 | 0.13 | 0.13 |

- **UME가 모든 칸에서 ItemKNN보다 정확하다** (네 칸 모두 구간 < 0). 학습형 랭커는 H&M에서 그보다 더 높다.
- **차이는 데이터가 희소할수록 크다.** H&M은 같이 산 기록이 많아 ItemKNN도 강하다 (UME의 80 ~ 93%). Amazon은 고객 · 상품당 구매가 적어(리뷰 기반, 같은 상품 재구매 0건) 공동 구매 이웃이 거의 없어 ItemKNN이 인기보다도 낮다. 상품 텍스트 · 이미지로 일반화하는 UME가 이 차이를 메운다 — 논문의 "멀티모달 콘텐츠가 희소한 데이터에서 유리하다"는 해석과 같은 방향.
- **ItemKNN은 추천 상품 종류가 2배 넓다.** 다양성이 필요하면 UME 후보에 ItemKNN 후보를 섞는 경로(랭커 후보 확장)가 다음 후보다.
- 참고: 이 표의 Amazon UME 규칙 값(0.0101 · 0.0087)은 C3 · C4 절(0.0095 · 0.0087)과 조금 다르다. 선호 브랜드가 동점일 때 서비스와 같은 규칙(브랜드 id가 작은 쪽, `np.bincount`)으로 맞췄기 때문이다 (#78에서 평가 코드를 서비스 특성 함수로 바꾸며 수정). H&M은 브랜드 가산이 없어 같다. 같은 이유로 "학습형 랭커" 절의 Amazon 행(규칙 · 랭커 모두 예전 동점 규칙)과도 조금 다르지만 결론(Amazon은 랭커 효과 없음)은 그대로다.
