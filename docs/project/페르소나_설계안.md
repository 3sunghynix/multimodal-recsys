# 페르소나 기반 시뮬레이터 — 팀 검토안 v0.2

작성: 김광석 / 2026-10-29 / 유환·형우 리뷰 반영본. 설계 방향 동의, 선호 브랜드 선정과 백엔드 계약 최종 합의 대기.

## 1. 목적과 보고 기준

가상 고객이 추천을 받아 view → click → add_to_cart → purchase 로그를 남기도록 하는 시뮬레이터의 설계·설정안이다. 아직 실행 프로그램이나 신규 API 구현을 포함하지 않는다.

**주 보고 기준은 같은 페르소나 안에서 모델끼리 비교하는 것이다.** 탐색형 CTR과 충성형 CTR의 크기만 비교해 어느 모델이 좋다고 판단하지 않는다. Amazon에서는 신규 브랜드·상품이 많아 novelty는 대부분 1이고 브랜드·동일 상품 재구매 적합도는 대부분 0이어서, 현재 가중치만으로도 유형별 클릭 확률의 기저 수준이 다를 수 있다. 이는 페르소나 설정의 특성이며 모델 성능의 증거가 아니다.

- 기준 모델은 `popularity`로 제안하고 실제 model_version_id와 설정을 실행 전 고정한다.
- 페르소나별 모델 상승률 = (후보 지표 − 같은 페르소나의 인기 모델 지표) / 인기 모델 지표.
- CTR 절대 차이(%p), 노출·클릭·고객 수와 source 노출 비중도 함께 보고한다. 기준값이 0이면 상승률은 계산 불가이며 건수와 절대 차이만 표시한다.
- 전체 요약은 미리 고정한 페르소나 비중으로만 보조 제시한다. 구성비 변경 효과를 모델 개선으로 해석하지 않는다.
- 파일럿은 기능 점검·기술적 비교다. 작은 표본의 상승률을 실제 고객 효과나 통계적으로 확정된 승리로 표현하지 않는다.

## 2. 페르소나와 첫 파일럿 범위

| ID | 이름 | 관심도 가중치(제안값 유지) | 첫 파일럿 |
|---|---|---|---|
| brand_loyal | 브랜드 충성형 | 브랜드 80%, 가격 15%, 탐색 5% | 포함 — 강한 브랜드 선호 스트레스 테스트 |
| price_sensitive | 가격 민감형 | 브랜드 10%, 가격 85%, 탐색 5% | 포함 |
| explorer | 탐색형 | 브랜드 5%, 가격 15%, 탐색 80% | 포함 |
| repeat_purchaser | 재구매형 | 브랜드 10%, 가격 10%, 동일 상품 재구매 80% | 포함 |
| trend_following | 트렌드 추종형 | 브랜드 10%, 가격 15%, 최근 인기 75% | 보류 — source별 특성 준비 후 추가 |
| new_item_seeking | 신상품 선호형 | 브랜드 10%, 가격 15%, 신규성 75% | 보류 — 유효한 날짜·정의 합의 후 추가 |

첫 파일럿은 **4종 각 100명, 총 400명**, 고객별 1세션·최대 10개 노출, seed 42, 초당 추천 요청 최대 2회를 제안한다. 실제 유효 고객 수·누락과 제외 사유를 보고하며 6종 완료로 표시하지 않는다. 초기 API·중복 방지·귀속 계약 확인 전 설정은 `write_events: false`다.

### 브랜드 충성형은 스트레스 테스트

유환의 EDA 공유값에 따르면 Amazon 고객의 최다 브랜드 비중 중앙값은 0.17이고 0.5 이상은 약 1.3%다. 이 수치는 본 PR에서 독립 재계산한 값이 아니다. 높은 브랜드 가중치를 둔 충성형은 실제 고객 분포를 재현한 것이 아니라 **강한 브랜드 선호 상황에서 추천이 어떻게 반응하는지 보는 스트레스 테스트용**이다. 페르소나 동일 비중 역시 실제 인구 비중 추정이 아니다.

### 신상품 판단 보류

현재 상품의 신뢰할 수 있는 출시·추가 날짜가 없다. 최초 이벤트 날짜는 출시일이 아니며, 특히 최근 13주만 자른 H&M에서 오래된 상품을 신상품처럼 보이게 만들 수 있다. 따라서 최초 이벤트일을 대체값으로 사용하지 않는다. 이름·날짜 정의 또는 다른 페르소나로의 대체를 합의한 뒤 추가한다.

## 3. 고객 선호·브랜드·초기 이력 선정

모델과 variant를 보기 전에 선호 카테고리·브랜드·예산·초기 이력을 고정하고 기록한다. 가상 고객은 source=sim이며 서로 다른 데이터셋 고객을 실제 동일인으로 연결하지 않는다.

**선호 브랜드 1~3개 선정 규칙은 아래 안으로 구체화하되 팀 확인을 받는다.**

1. 먼저 고객의 선호 카테고리를 고정한다. 분류는 통합 카테고리 매핑을 사용한다.
2. 해당 카테고리에서 train 구간에 등장하고 평가에 사용할 수 있는 브랜드·상품 풀을 만든다. 브랜드당 train 상품 최소 3개를 제안한다. 인기 상위 N개로만 제한하지 않는다.
3. 선호 브랜드 개수 N은 {1,2,3}에서 균등 추출하고 후보 브랜드 수로 제한한다. 후보 브랜드 중 균등·비복원 추출하며 인기 순 가중치는 주지 않는다.
4. 고객별 seed 파생 규칙, 선택 카테고리·브랜드와 사용한 풀 버전을 저장한다. 후보가 없으면 고객 생성 실패로 보고하며 몰래 다른 카테고리로 바꾸지 않는다.
5. 가상 초기 구매 이력은 선택한 브랜드의 train 상품을 이용해 합성한다. 실제 원본 고객 이력으로 표현하지 않는다. 이력을 backend에 넣는 방식·길이·균형은 형우·유환과 확인한다.
6. 초기 이력은 A/B 시작 이전 상태이며 실험 view/click/purchase 집계에 포함하지 않는다. 실험 중 관측 행동과 별도로 보존한다.

가격 예산은 선호 카테고리 내 train 가격의 25·50·75백분위에서 선택하는 초기안을 유지한다. 가격 출처(real/imputed/scaled)는 parquet 메타데이터를 참고하고 유형별 예상가 비중을 보고한다. DB price_source 열이 추가되기 전에는 이미 API가 반환한다고 가정하지 않는다.

재구매형은 비어 있지 않은 합성 초기 이력이 필요하다. v0.2의 재구매는 동일 상품 기준이며 유사 상품 재구매로 확장했다는 주장은 하지 않는다. 탐색형의 novelty 역시 비어 있지 않은 실험 전 이력을 기준으로 계산한다. 첫 파일럿의 선호 특성용 이력은 고정해 조건 변경을 줄인다.

## 4. 행동 규칙과 중립 전환율 점검

확률과 가중치는 현실 추정치가 아니라 제안된 합성 시험값이다. 기본 클릭 확률 4%, 클릭 후 장바구니 10%, 장바구니 후 구매 30%를 유지한다. 상품 선호 점수에 따라 클릭 확률만 설정 파일의 식으로 조정하며, 모델 점수·모델 이름·variant를 행동 입력으로 사용하지 않는다.

중립 점수, 10개 노출의 행동이 서로 독립이라는 가정 아래:

- 상품 한 개의 장바구니 확률 = 0.04 × 0.10 = 0.004.
- 세션에서 한 번 이상 장바구니 = 1 − (1−0.004)^10 ≈ **3.93%**.
- 상품 한 개의 구매 확률 = 0.04 × 0.10 × 0.30 = 0.0012.
- 세션에서 한 번 이상 구매 = 1 − (1−0.0012)^10 ≈ **1.19%**.

Retailrocket의 장바구니 세션 비율 약 2.49%, 구매 세션 비율 약 0.81%와 자릿수가 비슷해 시작값으로 유지한다. 동일하게 보정됐거나 분포가 재현됐다는 뜻은 아니다. 실제 선호 점수·상품 구성·행동 간 의존성에 따라 달라지며 이는 실측 시뮬레이션 결과가 아니다.

Retailrocket의 view와 추천 노출은 의미가 다를 수 있고, buy/cart 이벤트 수 비율은 개별 장바구니의 조건부 전환 확률이라고 단정하지 않는다. 원본 repeat_buyer_rate를 동일 상품 재구매율·브랜드 충성도로 사용하지 않는다.

## 5. source별 인기도 특성

트렌드형을 추가할 때 popularity_affinity는 다음 규칙으로 계산한다.

- Amazon과 H&M의 이벤트 수를 합산하거나 한 공통 날짜 창에 넣지 않는다. source마다 별도 집계·순위화한다.
- source별 events.parquet의 **split=train** 구간에서 마지막 날짜 D를 구한다. 그 source의 D−6일 00:00부터 D+1일 00:00 미만까지 7개 달력 날짜를 사용한다. 원본 타임스탬프 해석을 일관되게 적용한다.
- H&M은 2020년의 train 끝, Amazon은 2023년의 train 끝을 각각 사용한다. 현재 벽시계 날짜를 기준으로 창을 만들지 않는다.
- 이벤트 집계는 feedback>0인 구매 신호 행 수를 쓰는 안을 제안한다. +0.5와 +1의 가중 합이 아니라 건수로 셀지 유환과 확정한 뒤 트렌드형을 켠다.
- source의 카탈로그에 속한 상품을 대상으로 0건 상품도 포함해 백분위 순위를 계산한다. 동점은 평균 순위, 모든 값이 같으면 중립 0.5를 부여하고 해당 상태를 기록한다.
- 사용한 창·catalog·특성 버전을 실행 시작 전에 저장하고 실행 중 고정한다.

이렇게 하면 H&M의 상품당 이벤트 약 139개와 Amazon 약 24개라는 규모 차이가 특성 값을 직접 지배하는 것을 줄인다. 두 수치는 팀 공유값이다. source별 정규화만으로 노출 균형이 자동 보장되는 것은 아니므로 source 비중을 별도로 보고한다. 이 규칙은 시뮬레이터 특성 정의이며 서비스 인기 추천 모델 구현까지 변경했다는 뜻은 아니다.

## 6. 데이터 저장 위치 — 답변 반영

| 정보 | 확인된 위치·상태 | 사용 원칙 |
|---|---|---|
| feedback, split | DB에는 없음; processed/amazon_v2/events.parquet, processed/hm/events.parquet | 초기 이력·오프라인 평가 입력은 parquet의 train/고정 split에서 준비 |
| price | DB에 있음 | 상품 가격 참조 |
| price_source | 형우가 DB 열 추가 중 | 그 전에는 parquet 메타데이터로 보완; 반환 필드라고 가정하지 않음 |
| 상품 신규 날짜 | 현재 없음 | 신상품형 비활성화 |
| A/B 배정 | 서버가 고객·실험 해시로 결정 | 클라이언트가 variant를 재추첨하거나 바꾸지 않음 |
| created_at | 서버 수신 시각 | 지원되지 않는 논리 시각을 POST /events에 보내지 않음 |

원본 비연속 item_id와 DB items.id의 매핑을 확인한다. raw ID를 DB ID로 간주해 전송하지 않는다. 다중 브랜드 합성 고객 이력은 실제 데이터셋 간 고객 연결이 아니다.

## 7. 백엔드 계약과 중복 방지 — 실행 전 합의 필요

**현재 응답의 model_version_id·experiment_id·variant는 그대로 해당 노출과 후속 행동에 복사한다.** 전송 시점에 활성 모델을 다시 조회해 바꾸지 않는다.

형우가 제안한 다음 작업은 아직 구현 완료로 취급하지 않는다.

1. `POST /users {source, persona, source_user_id}`: 가상 고객 생성 API. 재시도 시 동일 사용자 처리와 초기 이력 적재 방식도 확인한다.
2. 추천 응답의 request_id 및 impression_id 또는 동등한 연결 키: 요청·상품 노출·행동을 연결한다. 한 요청 내 여러 상품은 각각 구분돼야 한다.
3. 이벤트 중복 방지: **논리 이벤트마다 클라이언트 UUID를 한 번 만들고 로컬에 저장하며, 재시도에는 같은 UUID를 쓰는 안**을 제안한다. UUID를 서버가 저장하고 unique key/upsert 등으로 중복을 막아야 효과가 있다.
4. purchase·click·view는 서로 다른 논리 이벤트다. impression_id 하나만 unique로 잡아 후속 행동을 서로 덮어쓰지 않도록, event_id 또는 이벤트별 유일성 규칙을 합의한다.
5. 한 상품을 다른 추천 요청에서 다시 노출하거나 정당하게 재구매하면 새 논리 이벤트다. 의도된 반복 행동과 통신 재전송을 구분한다.
6. 지원 전에는 event_id/request_id/impression_id 등 미지원 필드를 임의로 전송하지 않는다. UUID를 로컬에 생성한 것만으로 서버 중복 방지가 구현됐다고 하지 않는다.
7. 중복 방지 계약 전 POST 응답이 불명확하면 ‘전송 결과 불명’으로 남기고 자동 재전송·전체 파일럿을 중단한다. 조회로 확인하는 복구 방식은 서버 지원과 함께 정한다.

논리 세션 ID·순서·의도된 행동 시각은 별도 로컬 실행 기록에 저장한다. 서버 created_at은 수신 시각으로 유지한다. 짧은 파일럿을 실제 여러 날짜의 운영 효과로 표현하지 않는다.

보존할 기록: run_id, 설정·데이터 버전, seed, 고객 선호·초기 이력, 추천 응답 원문·상품 순서, 귀속 정보, 논리 이벤트 UUID, 행동 결정·시각, 전송 결과. seed만 같다고 모델 응답까지 같아지는 것은 아니므로 응답도 저장한다.

## 8. 평가·화면 표시

- 주 표는 페르소나별로 인기 모델과 후보 모델의 고객 수, 노출·클릭·장바구니·구매, CTR, CTR 차이(%p), 인기 대비 상승률을 나란히 둔다.
- 비교 구간·노출 개수·페르소나 구성·카탈로그·데이터 버전·seed 묶음을 고정한다. 그룹별 실제 배정 고객 수와 source·예상가 노출 비중을 함께 표시한다.
- 브랜드 충성형에는 ‘스트레스 테스트’ 라벨을 표시한다. 페르소나 간 CTR 순위를 모델 성능 순위처럼 보여주지 않는다.
- 브랜드 비중은 구매·클릭·노출 기준을 구분한다. 해당 행동이 없으면 계산 불가이며 유효 고객 수를 보고한다.
- 오프라인 Recall/NDCG/MAP는 고정 split으로 별도 계산한다. 어떤 feedback이 긍정 정답인지는 합의 후 기록하며 시뮬레이션 CTR과 같은 성능으로 합치지 않는다.
- 초기 파일럿의 소표본 결과는 기술적·탐색적 결과다. 정식 A/B 판정에서는 고객 단위 의존성과 여러 seed의 변동을 반영한 별도 계획이 필요하다.

## 9. 확정 사항과 남은 합의

리뷰 반영 완료: 페르소나 내 모델 비교, source별 인기도·train 날짜 창, 충성형 스트레스 테스트 표기, 중립 세션 확률 계산, 4종 400명 파일럿, parquet/DB 역할과 서버 시각 구분, 서버 A/B 귀속 유지.

남은 합의:

1. 선호 카테고리 기반 브랜드 균등 추출·최소 train 상품 3개 규칙을 승인할지. 초기 합성 이력 길이·DB 입력 방식.
2. 고객 생성 API의 확정 요청·응답, raw→DB ID 매핑 전달 방법.
3. request/impression/event ID의 최종 필드와 유일성 범위, 중복 방지·재전송 응답.
4. price_source 열·조회 지원 완료 시점.
5. 트렌드형 긍정 건수 집계 정의와 신상품형의 향후 정의.

승인 후: 실제 API 계약 확인 → 설정 로더·dry-run → 개발용 소량 전송 → 그룹별 건수 대조 → 4종 파일럿. 이 문서는 아직 API·시뮬레이터 실행 구현 완료 보고가 아니다.
