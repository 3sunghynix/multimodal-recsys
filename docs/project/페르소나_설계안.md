# 페르소나 기반 시뮬레이터 — 팀 검토안 v0.1

작성: 김광석 / 2026-10-29 / 상태: 팀 합의 전 초안

## 1. 이번에 만드는 것

가상 고객이 추천 목록을 보고 조회·클릭·장바구니·구매 행동을 남기도록 하는 시뮬레이터의 설정안이다. 이번 산출물은 `simulator/personas.yaml`과 설계 문서이며, 아직 API에 이벤트를 보내는 실행 프로그램은 아니다.

특정 모델의 승리를 보장하는 평가기가 아니라, 서로 다른 사용자 성향에서 서비스가 어떻게 동작하는지 확인하는 도구로 사용한다. 시뮬레이션 결과는 실제 고객 만족도나 매출 개선의 증거로 해석하지 않는다.

## 2. 페르소나 6종 제안

| ID | 이름 후보 | 쉽게 설명하면 | 점수 구성(가정) | 확인할 사항 |
|---|---|---|---|---|
| brand_loyal | 브랜드 충성형 | 선호 브랜드를 자주 선택 | 브랜드 80%, 가격 15%, 탐색 5% | 선호 브랜드 1~3개 선정 방법 |
| price_sensitive | 가격 민감형 | 같은 예산이면 저렴한 상품에 관심 | 브랜드 10%, 가격 85%, 탐색 5% | 카테고리별 예산과 예상가 처리 |
| trend_following | 트렌드 추종형 | 최근 인기 있는 상품에 관심 | 브랜드 10%, 가격 15%, 최근 인기 75% | 실제 유행이 아니라 최근 인기도를 대리 지표로 사용해도 되는지 |
| explorer | 탐색형 | 이전에 보지 않은 상품과 브랜드를 탐색 | 브랜드 5%, 가격 15%, 탐색 80% | 실험 전 이력 초기화 방법 |
| new_item_seeking | 신상품 선호형 | 최근 카탈로그에 추가된 상품에 관심 | 브랜드 10%, 가격 15%, 신규성 75% | 현재 스키마에 날짜가 없어 필드 또는 대체 유형 합의 필요 |
| repeat_purchaser | 재구매형 | 전에 구매한 상품을 다시 선택 | 브랜드 10%, 가격 10%, 재구매 80% | v0.1은 동일 상품 재구매만 구현할지 |

이름, 가중치, 유형별 고객 수는 모두 제안이다. Retailrocket에서 여섯 페르소나를 발견하거나 비중을 추정한 것이 아니다. 여섯 유형을 같은 수로 생성하는 것은 비교를 위한 균형 설계이며 실제 고객 구성 추정이 아니다.

## 3. 고객을 만드는 방법

1. `users.source = sim`인 별도 고객으로 생성한다.
2. 모델과 A/B 그룹을 보기 전에 페르소나, 선호 브랜드, 선호 카테고리, 예산과 초기 이력을 고정한다.
3. 초기 이력은 실제 데이터의 train 구간만 참고한다. valid/test의 구매를 선호 설정에 사용하지 않는다.
4. H&M 고객과 Amazon 고객을 동일인으로 연결하지 않는다. 다중 브랜드 시뮬레이션 고객의 합성 이력은 별도 생성 규칙을 기록하고, 실제 고객 이력으로 표시하지 않는다.
5. 예산은 선호 카테고리 내 train 카탈로그 가격의 25·50·75백분위 중 선택하는 방안을 제안한다. 외부 통화나 임의의 원화 금액을 넣지 않는다.
6. 참조할 상품은 적재된 `items.id`로 연결한다. 원본 상품 대조 시에는 `(source, source_item_id)`를 사용한다. Amazon ID가 연속이라는 가정을 하지 않는다.

초기 선호와 이력은 파일로 보존한다. 재구매형에는 비어 있지 않은 구매 이력이 필요하며, 탐색형 역시 이력이 없으면 모든 상품이 새 상품이 되어 구분력이 사라지므로 초기 이력을 만든다.

## 4. 행동 흐름과 시험용 확률

추천 요청 → 실제 표시된 상품에 view → 관심도에 따라 click → 클릭한 상품에 한해 add_to_cart → 장바구니에 넣은 상품에 한해 purchase 순서로 기록한다. v0.1은 하나의 단순한 경로를 구현하며, 실제 쇼핑에서 모든 구매가 이 경로를 따른다고 주장하지 않는다.

시험용 기본값은 다음과 같다.

- 관심도가 중간인 상품의 클릭 확률: 4%.
- 클릭 후 장바구니 확률: 10%.
- 장바구니 후 구매 확률: 30%.
- 클릭 확률은 고객·상품의 선호 점수가 높을수록 증가하도록 하되 0.5~30% 범위로 제한한다.

**이 세 확률은 구현을 시작하기 위한 임의의 시험값이다. Retailrocket에서 추정한 전환 확률이 아니며 실측값으로 표시하지 않는다.** 중립 점수에서는 노출 1건당 구매 확률이 0.04 × 0.10 × 0.30 = 0.0012, 즉 0.12%이지만, 이를 세션 구매율과 직접 비교해서는 안 된다. 노출 개수와 선택 간 의존성에 따라 세션 비율이 달라진다.

클릭 관심도는 각 특성(0~1)의 가중 평균이다. 관심도 0.5를 중립으로 두고 설정 파일의 부드러운 증가식을 적용한다. 이때 추천 모델 점수, 모델 이름, A/B variant는 고객 행동의 입력으로 사용하지 않는다. 확률은 결과를 본 뒤 특정 모델에 유리하게 바꾸지 않는다.

## 5. Retailrocket 통계를 사용하는 방법

참조 파일: `msrs_project/processed/retailrocket/sim_stats.json`. 현재 값은 공유받은 스크린샷에서 전사한 것으로, 실제 파일 및 집계 코드를 구현 전에 대조한다.

| 관찰 통계 | 값 | 사용 방식 |
|---|---:|---|
| 세션 분리 간격 | 30분 | 세션 경계를 정하는 참고 기준 |
| 세션 이벤트 수 | 중앙값 1, 90백분위 2, 99백분위 9 | 짧은 방문이 많다는 사실 참고 |
| 장바구니 포함 세션 비율 | 2.49% | 집계 의미를 맞춘 뒤 생성 결과와 대조 |
| 구매 포함 세션 비율 | 0.81% | 생성 세션의 구매 빈도 점검 |
| 장바구니/조회 이벤트 수 | 2.60% | 조건부 확률이 아닌 이벤트 수 비율 |
| 구매/장바구니 이벤트 수 | 32.39% | 개별 장바구니의 전환 확률이라고 단정하지 않음 |
| 상위 1% 상품의 조회 비중 | 22.7% | 관심 집중도를 비교하는 진단값 |

Retailrocket에는 현재 파일 기준 추천 노출 대비 클릭률이 없다. 따라서 이 통계로 클릭률 4%를 추정했다고 쓰지 않는다. `repeat_buyer_rate = 0.2198` 역시 집계 정의 확인 전 동일 상품 재구매율이나 브랜드 충성도로 사용하지 않는다.

우리 서비스의 view는 추천 노출이고, Retailrocket의 view와 같은 의미인지 확인되지 않았다. 추천 목록 10개 노출을 원본의 10회 상품 조회로 단순 비교하지 않는다. 원본 이벤트 비율은 합이 1이지만, 우리 로그에는 click·search도 있으므로 전체 이벤트 비율을 그대로 맞추지 않는다. 분위수 몇 개만으로 원본 세션 길이 분포를 정확하게 복원할 수도 없다.

먼저 공통 인기 모델 하나로 동작을 점검하고, 필요한 경우 train/개발 시뮬레이션에서만 보정한다. 이후 설정 버전을 고정하고 A/B 비교를 시작한다. 보정 과정에서 얻은 모델 비교 결과는 확증적 개선으로 보고하지 않는다.

## 6. 소규모 파일럿 제안

- seed: 42.
- 페르소나별 100명, 총 600명 계획.
- 고객별 세션 1회, 세션당 추천 최대 10개.
- 초당 추천 요청 최대 2회.
- 개발 환경에서만 실행. 초안 설정의 `write_events`는 false로 둔다.
- 필요한 특성이 없는 페르소나는 임의의 가짜 날짜·인기도로 채우지 않고 실행을 막아 보고한다. 일부 유형만 실행했다면 총 고객 수와 제외 유형을 정확히 표시한다.

신상품 날짜와 최근 인기도 계산이 준비되지 않았다면, 우선 브랜드 충성형·가격 민감형·탐색형·재구매형 4종의 파일럿을 제안할 수 있다. 이 경우 100명씩 총 400명이며, 6종 완료로 보고하지 않는다.

정상 기록 여부를 보는 파일럿이다. 이 표본만으로 모델의 우열이 통계적으로 입증됐다고 해석하지 않는다.

## 7. A/B와 로그 연결

- 그룹은 고객 단위로 일관되게 배정한다. 실제 배정은 서버 API를 확인하고 그 규칙을 따른다.
- 그룹 간 페르소나·선호·예산 분포가 비슷한지 확인하고 각 그룹의 고객 수를 기록한다.
- `experiment_id`, `variant`, `model_version_id`는 추천 응답에 연결된 값을 해당 노출 및 후속 행동에 유지한다. 구매 시점의 현재 활성 모델로 다시 조회해 덮어쓰지 않는다.
- 실행 ID·설정 버전·seed·추천 목록·상품 순서·행동 난수·시각을 별도 실행 기록에 보존한다. 아직 스키마에 없는 필드를 임의로 POST /events에 보내지 않는다.
- 동일 실행의 로그 전송 재시도가 중복 집계되지 않도록 백엔드와 중복 방지 방법을 합의한다.
- seed만 같다고 응답 순서·모델 버전이 달라진 실행이 재현되는 것은 아니므로 응답 자체도 보존한다.

정확한 요청 JSON과 고객 생성·이력 입력 방식은 실제 API를 확인한 후 구현한다. 아직 코드를 보지 않고 지원된다고 가정하지 않는다.

## 8. 평가 모듈과 연결

- 오프라인 Recall/NDCG/MAP: 제공된 고정 split 사용. 어떤 feedback을 긍정 정답으로 보는지 먼저 합의한다.
- 시뮬레이션 CTR: 표시된 상품의 노출 수와 클릭 수를 기준으로 정의하되, 같은 노출의 클릭을 한 번만 세는 등 분모·중복 기준을 고정한다.
- 브랜드 집중도: 팀의 최다 브랜드 비중 공식을 구매·클릭·노출별로 구분해 보고하는 안을 제안한다. 행동이 없는 고객을 0으로 간주하지 말고 유효 고객 수를 함께 기록한다.
- 다양성: 상품 중복, H&M 색상 변형 묶음 및 source별 노출 비중을 함께 확인한다.
- 사용자별·그룹별 고객 수, 노출 수, 클릭 수, 장바구니 수, 구매 수와 지표 분모를 함께 보존한다.

재구매형의 동일 상품 구매는 반복 구매이므로 오프라인 정답 중복 제거 규칙을 온라인 이벤트 수에 그대로 적용하지 않는다. 노출 재전송 중복과 의도된 반복 구매를 구분한다.

## 9. 팀에 확인할 항목

1. 페르소나 6종 이름과 최근 인기·카탈로그 신규성이라는 대리 정의를 승인할지.
2. 상품 추가 날짜가 없으면 필드를 추가할지, 신상품 선호형을 다른 유형으로 바꿀지.
3. `feedback`, `split`, `price_source`가 DB에 있는지, parquet에서 읽어야 하는지.
4. 고객 생성·초기 이력 입력 API 및 A/B 배정 방식.
5. 노출·클릭 연결과 전송 중복 방지 방식.
6. 임의 시험 확률과 동일 비중 600명 파일럿을 승인할지.

승인 후 순서: 실제 API 확인 → 설정 로더·행동 결정 로직 → dry-run → 작은 개발용 로그 전송 → 지표 대조 → 대시보드 연결.
