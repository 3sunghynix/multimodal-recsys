## 1. 추천 응답에 추가 (`GET /recommend/{user_id}`)

```jsonc
{
  "request_id": "6f1c…",            // 새로 추가: 서버가 만드는 UUID. 추천 요청 1건 = 1개
  "user_id": 123, "model": "ume", "model_version_id": 3, "experiment_id": 7, "variant": "B",
  "recommendations": [
    { "product_id": "40211", "score": 0.93, "score_kind": "model", "score_basis": "ume_zscore",
      "reason": "personalized", "is_exploration": false,
      "position": 1,                         // 새로 추가: 1부터, 화면 순서
      "impression_id": "6f1c…:1",            // 새로 추가: request_id + ":" + position (따로 저장하지 않음)
      "source": "amazon", "source_item_id": "B07XYZ" }   // 새로 추가: 시뮬레이터 상품 매핑 확인용
  ],
  "pipeline_latency": { … }, "session_context": { … }, "items": [40211, …]
}
```

- 서버는 응답할 때 **추천 기록 한 줄**을 저장한다 (새 테이블 `recommend_requests`, 2.1). 이 기록이 "무엇을 누구에게 어떤 모델로 보여 줬나"의 기준이다.
- `impression_id`는 `request_id`와 `position`으로 만들 수 있어서 별도 저장하지 않는다. 기존 필드는 그대로라 데모 화면 · 기존 테스트에 영향 없음.

## 2. 서버 변경

### 2.1 새 테이블 `recommend_requests` (Alembic 마이그레이션)

| 열 | 타입 | 설명 |
|---|---|---|
| request_id | UUID, PK | 응답의 `request_id` |
| user_id | FK users | |
| model_version_id · experiment_id · variant | | 응답과 같은 값 (서버가 정한 배정) |
| k | int | |
| item_ids | JSON (int 목록) | 보여 준 순서대로. position = 목록 위치 + 1 |
| created_at | datetime | |

추천 요청마다 insert 1건 (예상 +2 ~ 5ms, 추천 p95 102ms 기준 여유 있음).

### 2.2 이벤트에 추가 (`POST /events`)

| 필드 | 필수 | 규칙 |
|---|---|---|
| `request_id` | 추천에서 나온 행동이면 **필수** | `recommend_requests`에 있어야 함 (없으면 422). 그 요청의 `user_id`와 같아야 함 (다르면 422) |
| `position` | 선택 | 주면 그 요청의 해당 위치 상품이 `item_id`와 같아야 함. 안 주면 서버가 `item_id`로 찾아 채움. 요청 목록에 없는 상품이면 422 |
| `session_id` | 선택 | 2.4 |

- **`request_id`가 있으면 서버가 `model_version_id` · `experiment_id` · `variant`를 추천 기록에서 채운다.** 클라이언트가 보낸 값이 다르면 422. → 클라이언트가 모델 정보를 빼먹어도 모델별 CTR(`/metrics/window?model_version_id=`) · A/B 집계가 맞게 나온다 (#48 리뷰에서 남은 문제 해결).
- `request_id`가 없는 이벤트 = 추천과 무관한 행동 (검색 결과 클릭, 직접 상품 조회 등). 지금처럼 저장하되 모델 정보는 비어 있어 A/B · 모델별 집계에 들어가지 않는다.
- 멱등 비교 필드(`_IDEMPOTENT_FIELDS`)에 `request_id` · `position` · `session_id` 추가.

**`view`의 뜻:** 시뮬레이터 설정(`log_only_displayed_items_as_view: true`)과 A/B 집계(#42, 노출 = view)에 맞춰 **"추천 목록에서 화면에 보인 상품" = view, `request_id` 포함**으로 통일한다. 상세 페이지 조회는 `request_id` 없이 보내면 노출로 세지 않는다.

### 2.3 일괄 전송 `POST /events/batch`

```jsonc
// 요청: 최대 1,000건
{ "events": [ { EventIn }, { EventIn }, … ] }
// 응답 200: 입력 순서대로 건별 결과 (일부 실패해도 나머지는 저장)
{ "results": [ { "index": 0, "status": "created",   "id": 1001, "event_id": "…" },
               { "index": 1, "status": "duplicate", "id": 998,  "event_id": "…" },   // 같은 event_id · 같은 내용
               { "index": 2, "status": "error", "code": 422, "detail": "request_id 없음" } ],
  "created": 1, "duplicate": 1, "error": 1 }
```

- 건별 검증 · 멱등 규칙은 `POST /events`와 같다 (다른 내용으로 같은 `event_id` → 그 건만 `error` 409).
- 저장은 묶어서 한 번에 commit. Feature Store 반영도 묶어서 (is_setup 제외 규칙 동일).
- 이유: 로그 100만 건을 1건씩 보내면 요청 100만 번. 1,000건씩이면 1,000번.

### 2.4 세션 구분 `session_id`

- 지금 "현재 세션"은 서버 시각 기준 최근 30분이다. 시뮬레이터는 한 고객의 여러 세션을 몇 초 안에 이어서 보내므로 **세션이 하나로 합쳐진다** (세션 반영 · 세션 관심 소분류가 틀어짐).
- 규칙: 이벤트에 `session_id`가 있으면 **그 고객의 가장 최근 이벤트와 같은 `session_id`인 클릭**을 현재 세션으로 본다. 없으면 지금처럼 30분 규칙. 추천 요청에도 `?session_id=`를 받아 같은 규칙을 쓴다.
- 서버 시각(`created_at`)은 클라이언트가 바꿀 수 없다 (지표 창 · 재학습 기준이 흔들리지 않게).
- 담당: 세션 로직(`services/session.py` · Feature Store)은 김유환.

## 3. 시뮬레이터 API 모드 흐름 (광석)

### 3.1 실행 준비 — 격리
1. 실행마다 `run_id`를 만든다. 고객은 `POST /users {source: "sim", source_user_id: "<run_id>:<customer_id>", persona}` → 재시도해도 같은 고객.
2. 실행마다 A/B 실험을 새로 만든다 (`POST /experiments`, 인기 vs UME 50:50). 집계는 `experiment_id`로 이 실행만 본다. 실제 사용자 · 이전 실행과 섞이지 않는다.
3. 상품 매핑: 같은 DB에서 `export_simulator_items` snapshot (기존 절차). 추천 응답의 `source` · `source_item_id`로 매핑이 맞는지 건마다 확인하고, 틀리면 중단.

### 3.2 고객마다
1. 초기 이력: `POST /events/batch`로 구매 이력 `is_setup=True` (event_id는 `uuid5(run_id, customer, "setup", n)`).
2. 세션마다 (`session_id = "<run_id>:<customer_id>:s<번호>"`):
   1. `GET /recommend/{user_id}?k=10&session_id=…` → `request_id`, 상품 10개
   2. 행동 엔진으로 view · click · add_to_cart · purchase 결정 → 이벤트에 `request_id` · `position` · `session_id` · `event_id = uuid5(run_id, request_id, position, type)`
   3. 이벤트를 모아 `POST /events/batch` (고객 여러 명분을 1,000건 단위로)
3. 타임아웃 · 연결 오류는 같은 `event_id`로 재전송 (멱등). `error` 건은 기록하고 실행을 멈춘다 (설정 `on_ambiguous_post_before_idempotency`와 같은 원칙).

### 3.3 규모 계산 (명세: 고객 1만 · 로그 100만 이상)
- 세션당 view 10 + 클릭 · 장바구니 · 구매 약 0.5 → **세션당 약 10.5건**. 고객 1만 × 세션 10 = 10만 세션 → **약 105만 건** (초기 이력 별도) → `sessions_per_customer: 10`.
- 시간: 추천 10만 번 × 약 60ms ≈ 100분 (병렬 4개면 약 25 ~ 40분), 이벤트 일괄 1,050번. 11-17 대량 실행에 맞음.
