# 중간발표 데모 시나리오 (11-20)

> 검색 → 추천 → 세션 반영 → A/B → 재학습 → 후보 비교 → 교체 → 되돌리기. 약 6분.
> 수치는 11-18 전체 카탈로그 DB(상품 106,825 · 이벤트 107만, 운영 모델 `ume v1` id 3)에서 실측했다. 리허설 11-19.
> 필요한 PR: #62(대시보드 모델 교체), #63(재현 확인 수정).

## 0. 준비 (발표 30분 전)

```powershell
docker compose up -d
curl.exe -s localhost:8000/health                 # status ok
curl.exe -s localhost:8000/models                 # id 3 ume v1 = active 인지 확인 (아니면 activate 3)
```

- `.env`의 `HF_HUB_OFFLINE=1` (발표장 인터넷과 무관하게 시작).
- A/B 탭 결과 파일 (한 번만, `simulator/runs/`는 git 제외):
  ```powershell
  foreach ($n in 'catalog_pilot_10k', 'catalog_pilot_abc_10k') { mkdir -Force simulator/runs/$n | Out-Null; copy docs/project/${n}_summary.json simulator/runs/$n/catalog_ab_summary.json }
  ```
- **예열.** 첫 호출은 느리다 (H&M 첫 추천 0.67초, 모델 교체 직후 1.1초). 아래 3 · 4절 검색어와 고객을 한 번씩 미리 실행한다.
- 탭 미리 열기: 쇼핑 화면 http://localhost:8000/app/ · 대시보드 http://localhost:8501 · API 문서 http://localhost:8000/docs
- 재학습 후보가 이미 있으면(`retrain-...` candidate) 5절은 trainer 실행을 건너뛰고 비교 화면부터 보여 준다 (실행은 수 분).

## 1. 검색 (쇼핑 화면, 1분)

| 입력 | 보여 줄 것 | 실측 |
|---|---|---|
| `검은색 가죽 부츠` | 한국어 → `black leather boots` 변환, 가죽 컴뱃 부츠 | 101ms |
| `여름 꽃무늬 원피스` | `summer floral dress`, 플로럴 원피스 | 134ms |

| 이미지 업로드 (`data/dev_subset/images/amazon/10003.jpg`, 운동화) | 비슷한 Skechers 운동화 | 194ms |

말할 것: 텍스트 · 이미지 둘 다 같은 상품 공간에서 찾는다. 데이터셋별 순위를 따로 내서 섞는다. p95 146ms (목표 200ms).

## 2. 개인화 추천 (쇼핑 화면 고객 번호, 1분)

| 고객 | 이력 | 추천 (상위 8) | 실측 |
|---|---|---|---|
| **83229** (Amazon) | Amazon Essentials 남성 상의 5건 (셔츠 · 후드 · 카디건) | Amazon Essentials 남성 의류 7개 (스웨트팬츠 · 플리스 · 니트 · 청바지) | 72ms |
| **90409** (H&M) | 여성 바지 4건 · 벨트 · 상의 | 여성 바지 · 상의 · 블라우스 | 121ms |

말할 것: 이력 상품의 이미지 · 텍스트로 고객 벡터를 만들고(UME) 인기 · 선호 브랜드를 더한다. 같은 소분류는 30%까지만 (다양성 재정렬).

## 3. 세션 반영 · 신규 고객 (PowerShell + 쇼핑 화면, 1분)

쇼핑 화면에는 클릭 기록 버튼이 없어서 고객 생성 · 클릭만 PowerShell로 하고, 결과는 쇼핑 화면에서 보여 준다 (추천은 그 고객의 최근 세션 클릭을 자동 반영). Windows PowerShell 5.1은 주소에 `http://`가 필요하고 응답의 한글이 깨져 보이므로 결과 확인은 쇼핑 화면으로 한다.

```powershell
$A = "http://localhost:8000"
$u = (Invoke-RestMethod -Method Post "$A/users" -ContentType 'application/json' -Body (@{source='sim'; source_user_id="demo-$(Get-Random)"} | ConvertTo-Json)).id; $u
# → 쇼핑 화면에 고객 번호 $u 입력: 신규 고객이라 인기 상품 (사유 popular)
$s = "demo-$(Get-Random)"
foreach ($it in 86911, 86912) { Invoke-RestMethod -Method Post "$A/events" -ContentType 'application/json' -Body (@{event_id=[guid]::NewGuid().ToString(); user_id=$u; item_id=$it; type='click'; session_id=$s} | ConvertTo-Json) | Out-Null }
# → 쇼핑 화면에서 같은 고객 다시 추천: 원피스 · 점프수트가 위로
```

`86911` · `86912` = H&M "Aguilera maxidress" (여성 원피스). 데이터를 다시 적재했다면 id 확인:
`docker compose exec db psql -U recsys -d recsys -c "select id,title from items where source='hm' and category like '여성 > 원피스%' order by id limit 2 offset 5"`

| 단계 | 결과 (11-18) |
|---|---|
| 클릭 전 | 인기 상품 (H&M 카디건 · 바지 · 티셔츠), 사유 popular |
| 원피스 2개 클릭 후 | 세션 관심 = 원피스, 원피스 · 점프수트가 1 ~ 4위, 사유 personalized, 91ms |

**Amazon 상품으로 하지 말 것.** Amazon 1위 상품(티셔츠, 구매 1,417명)의 인기 가산점(+14)이 클릭 2개짜리 신호보다 커서 원피스가 안 올라온다. 이력이 강한 고객(83229)도 세션 비중 0.3이라 변화가 작다.

## 4. A/B (대시보드 › A/B 테스트 › A/B 시뮬레이션, 1분)

실제 카탈로그 · 추천 모델로 만든 모의 고객 1만 명 파일럿. "실제 카탈로그 파일럿" 선택 상자로 두 실행을 바꿔 보여 준다.

| 선택 | 화면 수치 | 말할 것 |
|---|---|---|
| `catalog_pilot_10k` (기본, A · B 각 5,000명) | 인기 34.6% vs UME 36.2%, 95% 구간 [−0.23%, +3.51%], **p = 0.086** | 전체는 유의하지 않다. 페르소나별로는 브랜드충성 **+13.2%p**, 실용주의자 **+6.0%p** (Bonferroni 후에도 유의), 트렌드세터 · 눈팅형은 소폭 감소 ([실제카탈로그_AB_파일럿.md](실제카탈로그_AB_파일럿.md)) |
| `catalog_pilot_abc_10k` (A · B · C 각 3,333명) | B − A +1.4%p (p = 0.23), **C(UME + 탐색) − B −2.2%p (p = 0.061)**, 신규 상품 노출 199개 (다른 그룹 5개) | 탐색 슬롯은 신규 상품을 보여 주는 대신 클릭을 조금 잃는다 — 탐색 비용 ([MAB_탐색.md](MAB_탐색.md)) |

오프라인 MAP 2 ~ 3배와 달리 전체 효과가 작은 이유 = 페르소나마다 클릭 이유가 다르다 (적합도 vs 인기 · 신규성). **서버 연결 대량 A/B는 진행 중**이라고 분명히 말한다.

## 5. 지속 학습 → 후보 비교 → 교체 → 되돌리기 (대시보드 › 모니터링, 2분)

```powershell
docker compose run --rm trainer          # 새 로그 1만 건 이상이면 학습 · 평가 · 후보 등록 (전체 카탈로그 수 분)
```

| 단계 | 화면 · 결과 (11-17 리허설) |
|---|---|
| trainer | 새 로그 107만 건 → H&M MAP@12 0.0425 → 0.0428, Amazon 0.0039 → 0.0041, 둘 다 채택 → 후보 `retrain-20261117-072202` 등록 |
| 모니터링 › 모델 버전 · 재학습 후보 | 버전 표(운영 중 3 · v1), 비교 표 4줄 판정 "통과". 규칙: MAP@12 ≥ 기준 × 0.98 그리고 Recall@20 ≥ 기준 × 0.90 |
| 운영 모델 교체 | 후보 선택 → 확인 체크(체크 전에는 버튼 잠김) → 교체 실행 |
| 쇼핑 화면에서 83229 다시 추천 | 응답 모델 버전이 후보로 바뀜 (첫 요청 1.1초, 이후 59 ~ 91ms) |
| 되돌리기 | 같은 화면에서 id 3 선택 → 교체 |

말할 것: 자동으로 바꾸지 않고 관리자가 비교를 보고 결정한다. 같은 평가 집합(evaluation_key)에서 잰 값끼리만 비교한다.

## 6. 예상 질문

| 질문 | 답 |
|---|---|
| 같은 옷이 여러 번 나온다 (H&M) | 같은 디자인의 색상 변형이다 (`product_code`가 같음). 결과에서 하나로 묶는 작업은 발표 후 |
| 이미 산 상품이 추천된다 | H&M은 재구매가 많아 오프라인 지표(MAP@12)에도 재구매가 포함된다. 서비스 정책(제외 여부)은 정할 일 |
| Amazon 추천에 엉뚱한 인기 티셔츠가 낀다 | 실제 데이터의 압도적 1위 상품이다. 인기 가중치 γ = 2는 오프라인 최적값이라 유지했고, 인기 점수 상한은 오프라인 재평가 후 결정 |
| A/B가 유의하지 않은데? | 전체는 유의하지 않음을 그대로 보고한다. 효과는 페르소나별로 갈린다 (브랜드충성 · 실용주의자 유의) |
| 재학습 개선폭이 작다 | 1 epoch 이어서 학습이고 로그가 기존 데이터라 작다. 시뮬레이터 로그가 쌓이면 같은 절차로 갱신 |

## 7. 문제가 생기면

| 증상 | 조치 |
|---|---|
| api `Exited (3)` | `.env` `HF_HUB_OFFLINE=1` 확인 후 `docker compose up -d api` |
| 검색 503 | `docker compose restart api` (PCA 파일은 시작 때 읽는다) |
| 첫 추천이 느림 | 예열 안 함 → 한 번 더 호출 |
| 교체 후 되돌리기를 잊음 | `curl.exe -X POST http://localhost:8000/models/3/activate` |
