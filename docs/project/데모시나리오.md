# 최종 데모 시나리오 (초안 11-26)

> 검색 → 추천 → 학습형 랭커 → 세션 반영 → A/B → 재학습 → 후보 비교 → 교체 → 되돌리기. 약 7분.
> 수치는 11-26 전체 카탈로그 DB(상품 106,825 · 이벤트 107만)에서 실측했다. 운영 모델 `ume v1-g1`(id 5), 랭커 버전 `ume v1-g1-rk`(id 6, 후보). id는 각자 DB에서 `curl localhost:8000/models`로 확인.
> 중간발표(11-20) 대본은 git 기록(#64)에 있다. **A/B · 재학습 절(4 · 5)은 A1 후속 · A4 결과가 나오면 갱신한다.**

## 0. 준비 (발표 30분 전)

```powershell
docker compose up -d
curl.exe -s localhost:8000/health                 # status ok
curl.exe -s localhost:8000/models                 # v1-g1 = active, v1-g1-rk = candidate 인지 확인
```

- `.env`의 `HF_HUB_OFFLINE=1` (발표장 인터넷과 무관하게 시작). `ADMIN_API_KEY`를 채웠다면 아래 `activate` 명령에 `-H "X-Admin-Key: <키>"`를 붙인다 (대시보드는 자동).
- 랭커 버전이 없으면 처음 한 번만 등록 (README "실행" 2절): `ranker_train` → `register_ume --version v1-g1-rk --ranker-root /data/models/ranker`. 이후 랭커 재학습은 trainer가 후보로 만든다.
- A/B 탭 결과 파일 (한 번만, `simulator/runs/`는 git 제외):
  ```powershell
  foreach ($n in 'catalog_pilot_10k', 'catalog_pilot_abc_10k') { mkdir -Force simulator/runs/$n | Out-Null; copy docs/project/${n}_summary.json simulator/runs/$n/catalog_ab_summary.json }
  ```
- **예열.** 첫 호출은 느리다 (신규 고객 첫 추천 0.2초, 모델 교체 직후 1초 안팎). 아래 검색어와 고객을 두 모델로 한 번씩 미리 실행한다.
- 탭 미리 열기: 쇼핑 화면 http://localhost:8000/app/ · 대시보드 http://localhost:8501 · API 문서 http://localhost:8000/docs

## 3. 학습형 랭커 (대시보드 교체 + 쇼핑 화면, 1분)

대시보드 › 모니터링 › 모델 버전에서 `v1-g1-rk`로 교체한 뒤 같은 고객을 다시 추천한다.

| 고객 | `v1-g1` (규칙) | `v1-g1-rk` (랭커) | 실측 p50 |
|---|---|---|---|
| 90409 (H&M) | Edda top · 바지 6개 · 남성 바지 | Pluto slacks · Edda top · Luna · Jade 데님 · **벨트** · **블라우스** · Madison · 남성 바지. 응답 `score_basis` = `ranker_probability` | 55 → 84 ~ 169ms |
| 83229 (Amazon) | (위 2절) | 같음 — Amazon은 랭커 효과가 없어 규칙 그대로 | 92 → 112ms |

말할 것: 규칙 점수 상위 300개를 GBDT가 다시 매긴다. 같은 이력에서 "산 옷의 다른 색" · 소분류 비율 · 가격대를 상품마다 다르게 쓰는 것을 배운다. 오프라인 H&M MAP@12 +36% · +18% (두 분할 유의), Amazon은 표본이 적어 효과 없음 → H&M만 켰다 ([추천모델설계.md](추천모델설계.md) "학습형 랭커"). 같은 조건 비교에서 인기 < ItemKNN < UME 규칙 < 랭커 ("비교 모델" 절).

**최종 운영 모델을 랭커로 할지는 팀 결정 (다음작업 ③).** 유지하면 이 절 끝에 `v1-g1`로 되돌린다.

## 4. 세션 반영 · 신규 고객 (PowerShell + 쇼핑 화면, 1분)

쇼핑 화면에는 클릭 기록 버튼이 없어서 고객 생성 · 클릭만 PowerShell로 하고, 결과는 쇼핑 화면에서 보여 준다 (D3가 들어오면 화면에서). Windows PowerShell 5.1은 주소에 `http://`가 필요하고 응답의 한글이 깨져 보이므로 결과 확인은 쇼핑 화면으로 한다.

```powershell
$A = "http://localhost:8000"
$u = (Invoke-RestMethod -Method Post "$A/users" -ContentType 'application/json' -Body (@{source='sim'; source_user_id="demo-$(Get-Random)"} | ConvertTo-Json)).id; $u
# → 쇼핑 화면에 고객 번호 $u 입력: 신규 고객이라 인기 상품 (사유 popular)
$s = "demo-$(Get-Random)"
foreach ($it in 86911, 86912) { Invoke-RestMethod -Method Post "$A/events" -ContentType 'application/json' -Body (@{event_id=[guid]::NewGuid().ToString(); user_id=$u; item_id=$it; type='click'; session_id=$s} | ConvertTo-Json) | Out-Null }
# → 쇼핑 화면에서 같은 고객 다시 추천: 원피스 · 점프수트가 위로
```

`86911` · `86912` = H&M "Aguilera maxidress" (여성 원피스). 데이터를 다시 적재했다면 id 확인:
`docker compose exec db psql -U recsys -d recsys -c "select id,title from items where source='hm' and category like '여성 > 원피스%' order by id limit 2 offset 5"`

| 단계 | 결과 (11-26) |
|---|---|
| 클릭 전 | 인기 상품 (H&M 카디건 · 바지 · 티셔츠 · 레깅스), 사유 popular |
| 원피스 2개 클릭 후 | 세션 관심 = 원피스, 원피스 · 점프수트가 상위 5개 중 5개 (Aguilera · Elton maxi · Joscelyn · Alcazar · Twist), 사유 personalized, 93ms |

시뮬레이터 고객(`source='sim'`)은 인기 집계에서 빠지므로 데모를 여러 번 해도 인기 순위가 바뀌지 않는다.

## 5. A/B (대시보드 › A/B 테스트, 1분)

> **A1 후속 · A4 대량 실행 결과가 나오면 이 절을 서버 A/B 라이브 통계(`/experiments/{id}/stats`)로 바꾼다.** 그 전까지는 파일럿 결과.

| 선택 | 화면 수치 | 말할 것 |
|---|---|---|
| `catalog_pilot_10k` (A · B 각 5,000명) | 인기 34.6% vs UME 36.2%, 95% 구간 [−0.23%, +3.51%], **p = 0.086** | 전체는 유의하지 않다. 페르소나별로는 브랜드충성 **+13.2%p**, 실용주의자 **+6.0%p** (Bonferroni 후에도 유의) ([실제카탈로그_AB_파일럿.md](실제카탈로그_AB_파일럿.md)) |
| `catalog_pilot_abc_10k` (A · B · C 각 3,333명) | B − A +1.4%p (p = 0.23), **C(UME + 탐색) − B −2.2%p (p = 0.061)**, 신규 상품 노출 199개 | 탐색 슬롯은 신규 상품을 보여 주는 대신 클릭을 조금 잃는다 ([MAB_탐색.md](MAB_탐색.md)) |

## 6. 지속 학습 → 후보 비교 → 교체 → 되돌리기 (대시보드 › 모니터링, 2분)

> **A4 결과(시뮬레이터 로그로 재학습)가 나오면 수치를 바꾼다.** 아래는 11-17 리허설.

```powershell
docker compose run --rm trainer          # 새 학습용 로그(클릭 · 장바구니 · 구매) 1만 건 이상이면 학습 · 평가 · 후보 등록
```

| 단계 | 화면 · 결과 (11-17 리허설) |
|---|---|
| trainer | H&M MAP@12 0.0425 → 0.0428, Amazon 0.0039 → 0.0041, 둘 다 채택 → 후보 `retrain-20261117-072202` 등록 |
| 모니터링 › 모델 버전 · 재학습 후보 | 비교 표 판정 "통과". 규칙: MAP@12 ≥ 기준 × 0.98 그리고 Recall@20 ≥ 기준 × 0.90 |
| 운영 모델 교체 | 후보 선택 → 확인 체크(체크 전에는 버튼 잠김) → 교체 실행 |
| 쇼핑 화면에서 83229 다시 추천 | 응답 모델 버전이 후보로 바뀜 |
| 되돌리기 | 같은 화면에서 `v1-g1` 선택 → 교체 |

말할 것: CT 루프(`monitoring/ct.py`)가 서버 지표와 새 로그 수를 보고 trainer를 부르지만, 교체는 관리자가 비교를 보고 결정한다. 교체 API는 관리자 키로 보호된다.

## 7. 예상 질문

| 질문 | 답 |
|---|---|
| 이미 산 상품이 추천된다 (H&M) | H&M은 재구매가 실제로 많아(정답의 5 ~ 7%) 남긴다 — 빼면 MAP가 절반 아래로 떨어진다. Amazon은 같은 상품 재구매가 로그에 한 건도 없어 뺀다 (`추천모델설계.md` "재구매 정책") |
| Amazon 추천에 인기 티셔츠가 낀다 | 실제 데이터의 압도적 1위 상품이다. 인기 가중치를 γ = 2 → 1로 낮춰 쏠림을 줄였다 (Amazon 목록 중 상위 1% 인기 상품 88% → 50%) |
| 협업 필터링(ItemKNN)보다 나은가? | 같은 조건에서 UME가 네 칸 모두 더 정확하다. Amazon처럼 구매가 희소하면 차이가 크다(ItemKNN −86 ~ −90%) — 콘텐츠(텍스트 · 이미지)로 일반화하기 때문. 대신 ItemKNN은 추천 상품 종류가 2배 넓다 |
| 랭커가 Amazon에는 왜 없나? | 오프라인에서 효과가 없었다 (양성 표본 800 ~ 1,300개, 후보 재현율 11 ~ 14%). 근거가 있는 데이터셋에만 켰다 |
| A/B가 유의하지 않은데? | 전체는 유의하지 않음을 그대로 보고한다. 효과는 페르소나별로 갈린다 (브랜드충성 · 실용주의자 유의) |
| 재학습 개선폭이 작다 | 1 epoch 이어서 학습이고 기존 데이터라 작다. 시뮬레이터 로그로 같은 절차를 다시 돌린다 (A4) |

## 8. 문제가 생기면

| 증상 | 조치 |
|---|---|
| api `Exited (3)` 또는 검색만 503 | 검색 모델을 못 읽은 것 (#79부터 api는 살아 있고 검색만 503). `.env` `HF_HUB_OFFLINE=1` 확인 후 `docker compose restart api` |
| 첫 추천이 느림 | 예열 안 함 → 한 번 더 호출 |
| 랭커 버전인데 H&M 고객 `score_basis`가 `ume_zscore` | 랭커 파일 없음 (서빙은 조용히 규칙 점수로 돌아간다) → 그 버전 params의 `ranker` 폴더 확인. 처음 등록 전이면 `ranker_train` → `register_ume --ranker-root` (운영 중인 폴더는 덮어쓰지 않는다) |
| 교체 시 401 | `ADMIN_API_KEY`가 api · 대시보드에 같은 값인지 확인 |
| 교체 후 되돌리기를 잊음 | `curl.exe -X POST http://localhost:8000/models/5/activate` (키를 쓰면 `-H "X-Admin-Key: <키>"`) |
