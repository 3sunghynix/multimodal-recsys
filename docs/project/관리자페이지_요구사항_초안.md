## 1. 목적과 이번 주 범위

관리자가 모델의 성능과 데이터 상태를 보고, 비교 실험을 관리하며, 근거를 확인한 뒤 모델을 교체하도록 돕는다. 숫자를 보여주는 화면과 모델 교체·재학습 같은 상태 변경 동작을 구분한다.

이번 주 산출물은 화면별 요구사항, [지표 정의](지표정의.md), 운영 정책 초안, API 차이 목록이다. 그래프 종류는 아래에 제안하되 Figma 화면 제작과 Streamlit/React 선정은 다음 단계로 둔다. 알림·재학습 자동화를 이미 구현했다고 표시하지 않는다.

## 2. 여섯 화면

### 2.1 개요

- **보여줄 것:** 현재 활성 모델과 버전, 실행 중 실험, 최근 평가 완료 시각, CTR·구매 수 추이, 페르소나별 인기 모델 대비 변화, 데이터 갱신 상태, 열린 알림, 진행 중인 작업.
- **할 수 있는 것:** 날짜·source·페르소나·실제/시뮬레이션 필터 변경, 관련 상세 화면으로 이동. 이 화면에서 즉시 모델 교체하지 않는다.
- **필요한 데이터:** 모델·실험 목록, 기간별 지표, 데이터 버전/규모, 알림/작업 상태, 집계 지연 및 분모.
- **그래프:** 시간별 CTR 선 그래프, 상태 카드. 데이터가 없으면 0 대신 ‘수집 전/계산 불가’를 구분.

### 2.2 모델 실험실

- **보여줄 것:** 동일 조건에서 모델 3~4개의 Recall/NDCG/MAP@12, 커버리지, 다양성, 브랜드 비중, 지연 시간, 유효 고객 수, 신뢰구간과 데이터/벡터 버전.
- **할 수 있는 것:** 비교 모델·기준 모델 선택, 평가 실행 요청, 결과 상세·설정 열기, 결과 내보내기, 권한 있는 관리자의 교체 요청과 확인.
- **필요한 데이터:** 평가 작업, 지표 이력·metadata, 모델 레지스트리, 교체 기록. 조건이 다르면 직접 순위를 매기지 않고 불일치 안내.
- **그래프:** 지표별 막대+신뢰구간, 정확도–다양성 산점도, 지연 시간 비교. 단위가 다른 값을 하나의 공통 축으로 합치지 않는다.

### 2.3 A/B 테스트

- **보여줄 것:** 실험 목적·주 지표·배정 비율, 기간, 그룹별 노출 고객·노출·클릭·구매, CTR 차이와 구간, 페르소나/source 분포, ‘수집 중/판정 가능/불확실’ 상태.
- **할 수 있는 것:** 모델·가중치·판정 계획을 지정해 실험 생성, 상세 확인, 중지. 실험 생성 시 현재 코드는 기존 running 실험을 중지하므로 사전 확인 필수.
- **필요한 데이터:** 실험 설정, 고객 배정 및 노출 귀속, 기간별 고객 단위 집계, 판정 프로토콜, 결과 구간. 현재 누적 CTR만으로 통계적 승자를 선언하지 않는다.
- **그래프:** CTR 시간 추이, 누적 표본 곡선, 그룹별 점추정+신뢰구간, 고객 구성 막대. 시뮬레이션의 주 결과는 동일 페르소나 안에서 인기 모델 대비 비교하고 source 구성도 함께 확인한다.

### 2.4 알림·재학습

- **보여줄 것:** 알림 지표·기준·하락률·관측 구간·분모, 작업 상태(대기/실행/성공/실패), 학습 데이터 범위, 후보 평가와 미채택 이유.
- **할 수 있는 것:** 알림 확인·해제, 관련 결과 열기, 관리자 재학습 요청·취소, 실패 로그 열기. 학습 성공과 운영 채택을 분리한다.
- **필요한 데이터:** 비중복 지표 구간, 알림 규칙과 기록, 학습 작업·로그, 산출물 버전, 평가 결과.
- **그래프:** 기준선이 있는 지표 추이, 작업 타임라인.

### 2.5 시뮬레이터 제어

- **보여줄 것:** 활성 페르소나 4종(브랜드 충성형·가격 민감형·탐색형·재구매형), 고객 수·비중·seed·속도·설정 버전, 대상 모델/실험, 진행률, 이벤트·실패·중복 수. 합성 데이터와 스트레스 테스트임을 표시한다.
- **할 수 있는 것:** 설정 검증·dry-run·실행 기록 내려받기. 실제 시작·중지는 고객 생성과 노출 연결·중복 방지 계약을 합의하고 구현한 뒤 활성화한다. 실행 중 설정 변경은 새 run으로 기록한다.
- **필요한 데이터:** personas.yaml v0.2, train 구간 초기 이력, source별 상품 속성, DB ID 대응표, 추천 응답의 귀속 정보, 실행 상태·로컬 논리 시간·서버 수신 시각.
- **그래프:** 같은 페르소나 안에서 모델별 CTR과 인기 모델 대비 상승률, 절대 차이(%p), 노출·고객 수. source 구성과 예상가 비중도 함께 표시한다. 서로 다른 페르소나의 원시 CTR 순위로 모델 우열을 판단하지 않는다.
- **파일럿 규모 제안:** 4종 × 100명 = 400명. 트렌드 추종형은 source별 인기도 구현·검증 후, 신상품형은 날짜 정의 합의 후 추가한다.

#### 결과 해석과 특성 계산 기준

1. 탐색형은 기본 novelty가 높고 브랜드·재구매 특성은 대부분 0일 수 있다. 따라서 페르소나별 CTR 차이는 확률 설정 차이도 반영한다. 주 비교는 동일 페르소나·조건에서 후보 모델과 인기 모델을 비교하는 것이다.
2. 상승률 = (후보 CTR − 인기 모델 CTR) / 인기 모델 CTR × 100%. 기준 CTR이 0이면 상승률은 계산 불가로 두고 절대 차이와 표본 수를 표시한다. 전체 요약은 고정된 페르소나 구성일 때만 보조 지표로 제시한다.
3. 인기도는 source별 train 데이터만 사용한다. 최근 7일은 각 source의 train 마지막 날짜를 기준으로 잡는다. H&M(2020년)과 Amazon(2023년)을 하나의 전역 날짜 창이나 원시 이벤트 수로 비교하지 않는다. 동일 source 안에서 정규화하고 실행 동안 고정한다.
4. 브랜드 충성형은 실제 고객을 대표하기보다 강한 브랜드 선호 상황을 확인하는 스트레스 테스트다. 팀 EDA의 Amazon 최다 브랜드 비중 중앙값 약 0.17, 0.5 이상 약 1.3%를 설정의 실측 근거로 오해하지 않는다.
5. 선호 브랜드는 선호 카테고리의 train 상품에서 1~3개를 균등 추출하는 안이다. 브랜드별 최소 상품 3개, 초기 이력 길이·적재 방식은 추가 합의 대상이다. seed·후보 집합·선정 결과를 보존한다.
6. 신상품 날짜가 없어 첫 이벤트 날짜를 출시일로 간주하지 않는다. 특히 H&M의 잘린 관측 기간은 오래된 상품을 신상품처럼 보이게 할 수 있다.
7. 중립 설정의 10개 노출 세션 장바구니율 약 3.9%, 구매율 약 1.2%는 독립 행동 가정에 따른 계산값이다. Retailrocket의 관측 규모와 비슷한 출발점일 뿐, 실제 전환율 재현이나 확률 보정 완료를 의미하지 않는다.

### 2.6 데이터 현황

- **보여줄 것:** source별 상품·고객·브랜드·이벤트 수, train/valid/test 규모, warm/cold 고객 수, 이미지·임베딩·가격·브랜드 누락률, 예상가 비중, 데이터 버전과 마지막 적재 시각.
- **할 수 있는 것:** 검사 실행 요청, source/버전별 상세 확인, manifest 대조 결과 열기. 원본 공개 다운로드나 데이터 삭제는 MVP 기능에 넣지 않는다.
- **필요한 데이터:** 카탈로그/이벤트 통계, split·feedback·price_source, 품질 검사 결과와 manifest metadata. source가 모든 DB 테이블에 이미 있다는 가정은 하지 않는다.
- **그래프:** source별 규모 막대, split 구성 누적 막대, 품질 검사 표.

## 3. 지표와 갱신

숫자의 공식·분모·제외 조건·갱신은 [지표정의](지표정의.md)를 단일 기준으로 사용한다. 오프라인 대표 구현은 `recsys/eval/metrics.py`, 독립 검증용은 `recsys/eval/reference.py`, 온라인 최다 브랜드 비중은 `recsys/eval/online.py`다. 화면과 평가 모듈에서 별도의 Recall·MAP 공식을 만들지 않는다.

화면 조회 주기는 개요/A/B/작업 30초, 실행 중 시뮬레이터 2초, 데이터 현황 5분을 **초안**으로 제안한다. 오프라인 평가는 버튼 또는 작업 완료 시에만 재계산하며, 페이지를 새로고침했다고 재학습하거나 테스트 평가를 반복하지 않는다.

공통 결과 필수 정보: 모델 버전, 데이터·벡터 버전, split, cohort, 긍정 정답 기준, K, 지표 정의 버전, 기간, 평가 시각, 유효/제외 건수. 누락 정보가 있으면 비교 불가로 표시한다.

## 4. 운영 정책 — 모두 제안값, 아직 구현·승인 아님

숫자는 토론을 시작하기 위한 MVP 가정이다. 실제 서비스 안정성·통계 검정력을 입증한 값이 아니며 환경과 표본을 확인해 조정한다. 시뮬레이션의 좋은 결과가 실제 사용자 효과를 보장하지 않는다.

### 4.1 지표 하락 알림

- 주 감시 지표는 CTR을 제안하되 노출·클릭 귀속 정의가 구현된 뒤 적용한다.
- 비교 기준은 동일 모델·source·고객 구성의 고정된 이전 정상 구간으로 둔다. 실제 로그와 시뮬레이션 로그를 같은 기준에 섞지 않는다.
- 상대 하락 10% 이상, 현재 각 1시간 비중복 구간에서 노출 5,000건·노출 고객 200명 이상, 3개 구간 연속이면 경고하는 안을 제안한다. 이는 통계적 유의성 검정이 아니라 운영 경보 조건이다.
- 기준 구간도 최소 표본을 만족해야 한다. 기준 CTR=0, 누락·적재 지연·표본 부족이면 하락률을 계산하지 않고 데이터 상태를 알린다.
- 동일 원인의 연속 알림은 하나로 묶고 확인/해제 이력을 보존한다. 정상 표본을 갖춘 3개 구간이 회복되면 해제 후보로 둔다.
- 데이터·모델 버전 변경이나 페르소나 비율 변경은 별도 구간으로 분리한다. 단순 합산 CTR 변화만으로 모델 퇴보를 확정하지 않는다.

### 4.2 A/B 판정

- 실험 전에 주 지표 1개, 가드레일, 고객 배정 단위, 종료 시점, 최소 개선 폭을 고정한다. 모델 두 개 비교를 MVP 기본으로 한다.
- 실제 트래픽의 임시 시작 기준: 최소 7일, 그룹별 노출 고객 500명·노출 10,000건·클릭 100건. 이는 검정력 계산을 대신하지 않으며 필요 표본은 기준 CTR과 최소 검출 효과로 추가 산정한다.
- 같은 고객의 여러 노출은 독립 표본으로 간주하지 않는다. 고정 종료 시점에 고객 단위 재표집으로 두 그룹 CTR 차이의 95% 구간을 계산하는 방안을 제안한다. 집계 CTR은 고객 클러스터별 클릭·노출 합계를 재표집해 계산한다.
- 차이의 하한이 0보다 크고 가드레일을 만족할 때 승자 후보. 구간이 0을 포함하면 ‘차이 불확실’이며 ‘두 모델 동일’이 아니다. 모델 3~4개를 동시에 검정하면 사전 비교군과 다중 비교 보정도 필요하다.
- 화면을 볼 때마다 유의성을 재판정해 조기 종료하지 않는다. 조기 판정은 별도의 순차 검정 계획이 있는 경우만 허용한다.
- 시뮬레이션 실험은 실제 7일 효과로 표현하지 않는다. 같은 시나리오·고객 구성으로 최소 3개 seed의 배치 비교를 제안하고, 사용자 표본 구간과 시뮬레이터 seed 간 변동을 구분해 보고한다.
- 현재 API의 누적 그룹 합계만으로 고객 단위 신뢰구간을 계산할 수 없다. 노출 귀속/고객별 집계 확장 전에는 통계적 승자 판정을 비활성화한다.

### 4.3 재학습

- 임시 트리거: 마지막 채택 이후 유효 신규 학습 신호 10,000건 이상이며 마지막 학습 후 24시간 경과. 단순 view 수가 아니라 긍정·부정 feedback 정의에 맞는 학습 신호 수를 센다. 부정 신호가 누락되는 현재 DB 상태라면 먼저 저장 경로를 합의한다.
- 새 이벤트는 원본 고정 test/valid 분할에 무작위로 합치지 않는다. 학습 컷오프와 데이터 버전을 별도로 기록하고 미래 이벤트를 이전 평가에 사용하지 않는다.
- 동시 학습 작업은 MVP에서 1개, 같은 데이터·설정의 중복 실행은 차단한다.
- 학습 성공 시 candidate로 등록한다. 자동 activate하지 않는다. 학습 실패·평가 누락·품질 미달이면 현재 active를 유지하고 사유를 남긴다.
- 튜닝·채택 판단은 validation에서 먼저 한다. 고정 test는 사전 계획된 최종 비교에 사용하며, 같은 test를 반복 관찰해 설정을 고르는 과정을 확증 결과라고 부르지 않는다.
- 임시 채택 가드레일: validation MAP@12가 기준보다 낮지 않고 Recall@12의 상대 하락이 1% 이내, 지연 p95가 합의 예산 안이며 데이터 품질 통과. 표본 불확실성까지 반영한 비열등성 마진·구간 기준은 유환과 확정 전까지 자동 판정을 막는다.

### 4.4 모델 교체와 롤백

- 1차: 기준/후보 모델 버전, 동일 평가 조건, 성능 차이·지연·제외 고객 수를 확인한다.
- 2차: 관리자에게 교체 대상과 영향을 다시 표시하고 확인을 받는다. UI 확인은 서버 인증·권한 검증을 대체하지 않는다.
- 서버에서 후보 유효성·산출물 존재·현재 active 버전을 확인하고 교체를 원자적으로 처리한다. 실행 중 A/B와의 충돌 정책도 확인한다.
- 교체 전 active ID, 새 ID, 요청자, 시각, 근거 평가 ID를 감사 기록으로 남긴다.
- 롤백은 마지막 정상 버전을 다시 활성화하되 동일 확인·권한·감사 절차를 따른다. 이전 산출물을 보존한다.
- MVP는 경보만으로 자동 롤백하지 않는다. 잘못된 배포/서빙 오류와 표본 부족을 구분해 관리자가 판단한다.

## 5. API 요구사항 — 형우와 합의할 목록

경로 이름은 제안이며 이미 존재하는 API와 혼동하지 않는다. #19의 고정 split 평가·인기 기준선과 #20의 통합 검색은 현재 main에 포함된다. POST /search는 q·선택 file·text_weight·k를 받고 query_en·untranslated·items를 반환한다. GET /search 키워드 경로와 구분한다.

| 요구 | 현재 코드로 가능한 것 | 부족한 것·추가 제안 |
|---|---|---|
| 모델 목록·등록 | GET/POST /models, GET /models/available | 페이지에 필요한 생성 시각·평가 연결·산출물 검증·권한 |
| 모델 교체 | POST /models/{id}/activate | 조건부 교체/동시성 방지, 교체 감사 이력, 롤백 정책·이력 API |
| A/B 생성·목록·중지 | POST/GET /experiments, POST /experiments/{id}/stop | 생성 확인, 프로토콜·종료 시각·배정 고객 수 저장, 이름 중복 variant 검증 |
| 그룹별 수치 | GET /experiments/{id}/metrics: 누적 고객·view·click·purchase·CTR | start/end/source/persona 필터, 비중복 시간 구간, 고객별 클릭·노출 집계, 신뢰구간/판정 상태 |
| 지표 추이 | metric_snapshots 테이블만 존재, 조회/기록 라우터 없음 | GET/POST /metric-snapshots 또는 평가 결과 등록 API; 버전·기간·분모 metadata |
| 오프라인 평가 작업 | 없음 | POST /evaluations, GET /evaluations/{id}, 결과·오류·설정 기록 |
| 알림 | 없음 | GET /alerts, POST /alerts/{id}/acknowledge, 규칙·해제·이력 저장 |
| 재학습 | 없음 | POST /training-jobs, GET /training-jobs/{id}, 취소/진행/산출물·평가 연결 |
| 시뮬레이터 실행 | 없음 | POST /simulation-runs, GET /simulation-runs/{id}, 중지·설정 검증·dry-run |
| 가상 고객 생성 | 확인한 사본에는 users 테이블만 존재 | 형우가 POST /users {source, persona, source_user_id} 추가 예정이라고 답변. 배포 여부·응답 ID·초기 이력 적재 계약 확인 필요 |

| 이벤트 적재 | POST /events, GET /events/count | session_id/impression_id/run_id 또는 동등 연결, idempotency key, 귀속 검증, 원본 feedback/시각 지원 여부 |
| 데이터 현황 | 이벤트 type별 전체 건수만 가능 | GET /data/summary, GET /data/quality-runs/{id}, split/누락률/manifest 버전 |

### 팀 리뷰 후 추가된 API 합의 사항 — 구현 완료로 표시하지 않음

- 추천 응답에 이미 있는 model_version_id·experiment_id·variant는 이벤트에 그대로 복사한다. A/B 배정은 서버의 고객·실험 해시를 따른다. 클라이언트가 그룹을 새로 정하지 않는다.
- request_id 또는 impression_id로 추천 노출과 후속 이벤트를 연결하는 방안은 형우와 최종 합의한다. 임의 필드를 현재 API에 보내지 않는다.
- 이벤트마다 클라이언트 UUID를 한 번 만들고 재시도에 같은 값을 사용하는 방안을 제안한다. 서버의 유일성 제약·중복 처리 응답이 함께 필요하다. impression_id 하나만 유일 키로 쓰면 view·click·purchase가 서로 덮어써질 수 있다.
- 중복 방지 계약 전 POST 응답이 불명확하면 자동 재전송하지 않고 실행을 중지해 기록한다. 확인 전 파일럿은 dry-run으로 제한한다.
- feedback·split은 현재 parquet에만 있다. 초기 이력은 processed/{amazon_v2,hm}/events.parquet의 train에서 읽는다. price_source DB 열은 형우의 추가 예정 사항이며 완료 확인이 필요하다.
- created_at은 서버 시각이다. 시뮬레이션의 논리 시간은 별도 실행 기록에 보존하며 서버 시각을 덮어쓰는 기능이 있다고 가정하지 않는다.

### 이전 코드 사본에서 확인한 구체적 차이

- Event에는 feedback·split·session/impression ID가 없다. EventIn은 클라이언트 이벤트 시각도 받지 않아 서버 수신 시각이 기록된다. 시뮬레이션 논리 시간과 기간별 운영 평가를 혼동하지 않는다.
- Item에는 price_source와 상품 날짜가 없다. 관련 설계 문서의 결정 사항이 모두 DB에 반영됐다고 가정하지 않는다.
- GET /experiments/{id}/metrics의 users는 이벤트가 있는 고객 수이고 CTR은 원시 click/view다. 노출 귀속·중복 방지·통계 구간을 제공하지 않는다.
- activate는 이전 active를 candidate로 바꾸지만 교체 이력 테이블·평가 가드레일은 없다. 현재 동작을 ‘안전한 롤백 완료’라고 표시하지 않는다.
- 새로운 실험 생성은 기존 running 실험을 중지한다. 운영 화면에서 숨은 부작용으로 만들지 않는다.
- 현재 기본 인기 모델은 모든 Event를 참조한다. 고정 split 오프라인 비교에서 그대로 호출하면 test 이벤트를 볼 위험이 있다. 평가용 학습 스냅샷/기간/source 필터를 별도로 합의한다.
