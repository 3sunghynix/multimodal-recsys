# 검색 (텍스트 · 이미지 · 한국어)

> 코드: 점수 규칙 `recsys/search.py` = `backend/app/services/search_core.py` (같은 파일, 테스트로 확인), 한국어 `recsys/translate.py` = `backend/app/services/translate_ko.py`, API `backend/app/routers/search.py`
> 실험: `python -m recsys.search_eval --root <msrs_project>` (Colab, 2026-10-29)

## 1. 결정

| 항목 | 결정 | 근거 (아래 실험) |
|---|---|---|
| 텍스트 질의 | MiniLM → 상품 텍스트 임베딩 + Marqo 텍스트 → 상품 이미지 임베딩, **반씩** | 둘을 섞으면 하나만 쓸 때보다 정확도 +3 ~ 9%p. 5:5와 7:3은 거의 같음 |
| Marqo 텍스트 질의 | 이미지 PCA 평균을 **빼지 않음** | 빼면 정확도 0.32, 안 빼면 0.92 (텍스트는 이미지 평균과 멀어서 모든 질의가 한쪽으로 쏠림) |
| 데이터셋 결합 | **per_source_rank**: 데이터셋 안의 순위 백분위로 합침 → 카탈로그 비율대로 섞임 | 원래 점수는 텍스트가 들어간 방식에서 H&M 52 ~ 61%(카탈로그 19%), 표준화만으로는 질의마다 한쪽이 독차지(두 데이터셋 함께 18 ~ 53%). 순위 결합은 100% · H&M 20%, 정확도 비용 약 4%p |
| 한국어 | **패션 용어 사전**(약 240개) → 영어. 사전에 없는 단어는 응답 `untranslated`로 알림 | 번역 모델(opus-mt-ko-en)만 쓰면 0.69, 사전 0.91 (영어 0.93). 번역 모델은 청자켓 → "Celadon", 양말 → "Sheep's Horses" |
| 이미지 + 텍스트 | `text_weight : 1 − text_weight` (화면 우선순위 슬라이더, 기본 0.5) | |

## 2. 실험 결과 (상위 20)

질의 40쌍(영어 · 한국어). 정답 = 상품 제목 · 설명 · 카테고리가 질의 키워드 규칙을 만족 (예: "black dress" → dress 그리고 black). 키워드 판정이라 제목에 단어가 있는 상품에 유리하다.

| 언어 | 방식 | 결합 | 정확도 | H&M 비율 | 두 데이터셋 함께 |
|---|---|---|---:|---:|---:|
| 영어 | 텍스트 + 이미지 5:5 | 원래 점수 | 0.976 | 0.52 | 0.53 |
| 영어 | 텍스트 + 이미지 5:5 | **순위 결합** | **0.933** | **0.20** | **1.00** |
| 영어 | 텍스트(MiniLM)만 | 순위 결합 | 0.899 | 0.20 | 1.00 |
| 영어 | 이미지(Marqo 텍스트)만 | 순위 결합 | 0.896 | 0.20 | 1.00 |
| 한국어 · 번역 모델 | 텍스트 + 이미지 5:5 | 순위 결합 | 0.690 | 0.20 | 1.00 |
| **한국어 · 사전** | 텍스트 + 이미지 5:5 | **순위 결합** | **0.909** | **0.20** | **1.00** |

전체 표: 드라이브 `msrs_project/results/search/search_compare.csv`, 질의별 `search_per_query.csv`.
1차 실험에서 사전에 없던 벨벳 · 코듀로이는 번역 모델이 belvet · coduroy로 틀려 사전에 추가했다.

## 3. API — `POST /search` (multipart/form-data)

| 필드 | 기본 | 설명 |
|---|---|---|
| `q` | 없음 | 검색어 (한국어 · 영어) |
| `file` | 없음 | 검색 이미지 (jpeg · png · webp, 10MB 이하). `q`와 둘 중 하나는 필수 |
| `text_weight` | 0.5 | 둘 다 줄 때 텍스트 비중 (0 ~ 1) |
| `k` | 20 | 1 ~ 100 |
| `merge` | per_source_rank | per_source_z · global (비교 · 관리자 화면용) |
| `source` · `brand_id` | 없음 | 데이터셋 · 브랜드 한정 |

```bash
curl -X POST localhost:8000/search -F q="검은색 원피스" -F k=12
curl -X POST localhost:8000/search -F q="dress" -F file=@sample.jpg -F text_weight=0.3
```

응답:
```json
{"query": "검은색 원피스", "query_en": "black dress", "untranslated": [],
 "weights": {"text": 0.5, "text_image": 0.5}, "merge": "per_source_rank",
 "items": [{"id": 12, "source": "amazon", "brand_id": 3, "title": "...", "category": "...",
            "price": 29.9, "image_path": "...", "score": 1.0}]}
```

오류: 둘 다 없음 · merge 오타 422, 이미지 형식 415 · 크기 413 · 빈 파일 400, 인코더 · PCA 미설치 503.
점수는 서버 메모리에서 계산한다 (데이터셋별 결합에 데이터셋 전체 점수가 필요해 pgvector 상위 k로는 불가). 상품 10만 기준 약 200MB, 상품이 바뀌면 다음 요청에서 다시 읽는다.

**실행에 필요한 파일** (docker-compose가 `./data`를 `/data`로 연결): `data/embeddings/v2/pca_text.npz`, `pca_image.npz` + 상품 임베딩 적재 `python -m scripts.load_dev_subset --data /data/dev_subset --embeddings /data/embeddings/v2`. 처음 시작할 때 모델(MiniLM 90MB, Marqo 800MB)을 내려받는다.

## 4. 화면 (데모용 최소 구성)

```
[검색어 (한/영)              ] [이미지] [검색]
우선순위: 텍스트 ●━━━━○━━━━ 이미지        ← 텍스트 · 이미지를 둘 다 넣었을 때만 표시
"black dress"(으)로 검색했습니다           ← query_en, untranslated가 있으면 "번역 못한 단어: …"
[사진][사진][사진][사진]  … 상품명 · 브랜드 · 가격 (price_source가 real이 아니면 '예상가') · [H&M]/[Amazon]
```

화면이 할 일: `POST /search` 한 번 + 카드 그리기. 검색 로그는 `POST /events` (type=search, query)로 보낸다.

## 5. 남은 것

- 사전에 없는 단어: 지금은 알리기만 한다. 로그(`untranslated`)를 모아 사전에 추가하거나, 필요하면 다국어 인코더로 상품 임베딩을 다시 만든다.
- 키워드 정확도는 근사치다. 발표 전에 질의 몇 개는 사람이 직접 판정해 보완한다.
