# 상품 키워드 배지 (D4, 11-26)

> 코드: 계산 `recsys/review_badges.py`, 적재 `backend/scripts/load_badges.py`, 서빙 `backend/app/services/badges.py`, 화면 `backend/frontend/index.html`. 테스트: `backend/tests/test_badges.py`

상품 사진 · 설명으로는 알 수 없고 **사 본 사람 · 구매 데이터만 아는 정보**를 상품 카드의 짧은 키워드로 보여 준다 (예: 작게 나와요 · 착용감 좋음 · 비침 주의 · 체형 보정 · 출근룩 · 최근 인기). 크롭 · 소재명처럼 상품 정보에 이미 있는 것은 넣지 않는다.

| 종류 | 출처 | 대상 | 예 |
|---|---|---|---|
| 리뷰 배지 | Amazon 리뷰 본문 429만 건 (우리 카탈로그 상품, Amazon Reviews 2023) | Amazon | 정사이즈 · 작게 / 크게 나와요 · 착용감 · 품질 · 신축성 · 따뜻해요 / 시원해요 · 가성비 · 재구매 · 칭찬 · 비침 / 줄어듦 / 쉽게 해져요 주의 · 귀여운 · 체형 보정 · 섹시한 · 트렌디 · 우아한 · 출근룩 · 하객·행사룩 · 운동용 · 여행용 · 홈웨어 · 선물 추천 (25종) |
| 구매 로그 배지 | 서비스 DB 구매 로그 (요청 때 계산 · 캐시) | 두 데이터셋 | 최근 인기 · 급상승 |

H&M은 리뷰가 없어 구매 로그 배지만 붙는다.

## 1. 리뷰 배지 규칙

1. 리뷰마다 배지별 정규식으로 언급을 센다. 방향을 나눈다 (작게 / 크게 / 정사이즈, 따뜻해요 / 시원해요). 부정 · 회피 표현은 뺀다 ("don't size up", "didn't shrink", "no pilling", "wedding ring", "gift card" 등). 둥근 따옴표(’)는 '로 바꿔서 센다.
2. 상품의 언급 비율(언급 리뷰 / 리뷰)이 **같은 카테고리 평균의 1.5배 이상**이고 언급 3건 · 비율 5% 이상이면 후보. 흔한 표현("comfortable"은 리뷰의 26%)이 모든 상품에 붙지 않게 하려는 것. 카테고리는 3단계, 상품 30개 미만이면 2단계.
3. 맞서는 배지는 언급이 많은 쪽 하나만.
4. 핏 · 신축성 · 보온 · 비침 · 세탁 배지는 액세서리 · 가방 · 지갑에는 붙이지 않는다.
5. 상품당 최대 3개: 주의 배지 먼저, 그다음 카테고리 대비 배수 순.

근거는 API · 화면에 함께 나온다: "리뷰 412건 중 87건, 같은 카테고리의 2.3배".

### 결과 (Amazon 86,827개)

- 배지가 1개 이상 붙는 상품 **81.3%**, 붙으면 평균 2.0개.
- 가장 흔한 배지도 상품의 16% 정도 (품질 좋음 14,192 · 귀여운 14,172 · 착용감 좋음 11,053 · 작게 나와요 10,252 · 정사이즈 9,745). 가장 드문 것: 줄어듦·물빠짐 주의 717 · 쉽게 해져요 492.

### 정확도 점검 (언급 단위)

배지마다 전체 리뷰에서 무작위로 뽑은 근거 문장 20건(`data/badges/samples.json`)을 직접 읽고 그 배지 뜻이 맞는지 셌다. 처음 정규식에서 틀린 유형을 고친 뒤 다시 뽑았다.

| 배지 | 1차 | 고친 뒤 | 고친 것 · 남은 오류 예 |
|---|---|---|---|
| 정사이즈 · 작게 / 크게 나와요 | 80 ~ 90% | 95 ~ 100% | "don't size up", "not too tight", "writing too small" 제외 |
| 착용감 · 품질 · 따뜻해요 · 가성비 · 귀여운 · 체형 보정 · 트렌디 | 85 ~ 100% | 95 ~ 100% | "not super high quality", "ok for the price", "don't find it flattering" 제외 |
| 시원해요 | 65% | 90% | "lightweight"(가벼움 ≠ 시원함) 뺌. 남은 오류: "non breathable" |
| 재구매 · 칭찬 · 섹시한 · 우아한 | 80 ~ 95% | 90 ~ 95% | 남은 오류: "would order more but…", "compliments my earrings"(동사) |
| 비침 주의 | 65% | 85% | "isn't see through", "sheer aesthetics" 제외. 남은 오류: 스페인어 "no transparente", 원래 비치는 디자인 |
| 줄어듦·물빠짐 주의 | 45% | 85% | "didn’t shrink"(둥근 따옴표), "hoping it will shrink" 제외. 남은 오류: "hasnt shrunk"(따옴표 없음), "in case it shrinks" |
| 쉽게 해져요 | 25% | **100%** | "no pilling", "avoid pilling", "ripped off", "thumb holes" 제외, 구체적 표현(fell apart · pilled after · hole in the seam)만 |
| 출근룩 · 하객·행사룩 · 운동용 · 여행용 · 홈웨어 · 선물 | 55 ~ 95% | 85 ~ 95% | "going to work great", "wedding ring", "gift card" 제외. 남은 오류: "wouldn't wear to work out", "can't give as a gift" |

전체 500건 중 약 **94%**가 맞다. 배지는 상품마다 언급이 3건 이상 · 카테고리 대비 1.5배여야 붙으므로 개별 오류 문장 하나로 배지가 붙지는 않는다. 정밀도를 더 올리려면 다음 단계는 LLM 라벨링 (리뷰 본문은 Drive `exports/amazon_reviews_catalog.parquet`에 있음) — 데모 · 인기 상품 수천 개만 LLM, 나머지는 이 규칙.

## 2. 구매 로그 배지

| 배지 | 기준 |
|---|---|
| 최근 인기 | 최근 창(그 데이터셋 서비스 구매의 마지막 시각 기준 H&M 7일 · Amazon 28일) 구매 5건 이상이고 같은 카테고리 상위 3% |
| 급상승 | 최근 창 구매 8건 이상이고 직전 같은 길이 창의 3배 이상 |

- 서비스 인기 통계와 같은 범위 (비 setup 구매, 시뮬레이터 고객 제외 — `event_scope.service_users`). 쇼핑 화면 구매가 쌓이면 바뀐다.
- 처음 기준(상위 10% · 3건, 급상승 5건 · 2배)은 상품의 11% · 5%에 붙어 추천 목록 거의 전부가 "최근 인기"였다 → 위 기준으로 좁혔다.
- 캐시: `ume._popularity_z`와 같은 두 단계 (가장 큰 id 이벤트 한 행 → 바뀌었으면 그 데이터셋 마지막 구매 행). events 테이블에 기본 키 외 색인이 없어 매 요청 마지막 구매 행을 찾으면 검색이 3.5초까지 늘었다 (11-26 실측) — 두 단계로 바꾼 뒤 그대로.

## 3. 서빙 · 화면

- 저장: `item_badges` 테이블 (Alembic `0006_item_badges`, origin = review). 구매 로그 배지는 저장하지 않는다.
- API: `GET /items` · `POST /search`의 상품에 `badges` (카드용 최대 3개: 구매 로그 → 리뷰), `GET /items/{id}`는 전부. 각 배지 `label` · `kind` (trend · fit · good · caution · vibe · occasion) · `origin` (review · log) · `evidence`.
- 화면: 카드 가격 아래 칩 (최근 인기 · 급상승 주황, 주의 배지 ⚠ 빨간 테두리), 마우스를 올리면 근거. 상품 상세에 "구매자 키워드" 목록 (배지 + 근거).
- 응답 시간 (전체 카탈로그, 11-26): 카드 조회 `GET /items?ids=` 20개 p50 31ms, 검색 서버 시간 p50 166ms (배지 전과 같은 수준). 데이터셋별 구매 로그 배지 첫 계산 1 ~ 1.3초 (캐시 후 없음).

## 4. 실행

```bash
# 1) 리뷰 본문(Drive msrs_project/exports/amazon_reviews_catalog.parquet, 430MB)을 OneDrive 밖에 둔다 (예: C:\msrs_data\reviews)
# 2) 배지 계산 (약 15분) → data/badges/{amazon_review_badges.parquet, samples.json, summary.json}
docker compose --profile trainer run --rm -v C:/msrs_data/reviews:/reviews:ro trainer \
    python -m recsys.review_badges --reviews /reviews/amazon_reviews_catalog.parquet
# 3) 적재 (다시 실행해도 안전 — 리뷰 배지를 지우고 다시 넣는다)
docker compose exec api python -m scripts.load_badges --file /data/badges/amazon_review_badges.parquet
```

`data/badges/`는 git 제외. 다른 팀원은 Drive에 올린 `amazon_review_badges.parquet`(2MB)만 받아 3)을 하면 된다.
