# 지표 정의서 v0.1 — 평가 코드·관리자 화면 공통

상태: 팀 검토용. 코드 기준: `recsys/evaluation/metrics.py`. 공식·분모·예외 처리는 구현과 일치하며, 원본 데이터의 긍정 신호 선택과 운영 임계값은 별도 합의가 필요하다.

문서 보완: 페르소나 설계 v0.2의 보고 기준을 반영했다. 평가 공식과 코드 정의 버전은 v0.1을 유지한다. 아래 시뮬레이션 상승률·운영 집계는 추가 구현 대상이며 기존 평가 함수가 계산한다고 표시하지 않는다.

## 1. 공통 계약

- K는 양의 정수이며 기본값은 12다. MAP@12는 K=12로 계산한다. 필요하면 같은 코드에 K=20·50·300을 명시해 별도 지표로 기록한다.
- 모델 비교는 같은 데이터 버전, 고정 split, 긍정 정답 규칙, 고객 집합, 후보 카탈로그, 중복 정책으로 한다. 다른 조건의 숫자를 같은 순위표에서 직접 비교하지 않는다.
- 입력 `eligible_users`가 평가 고객 목록이다. Amazon의 warm-start 평가는 train 이력이 있는 테스트 고객 목록을 데이터 준비 단계에서 만든다. 함수가 임의로 고객을 다시 추출하지 않는다.
- 정답은 고객별 긍정 상품의 집합이다. 동일 고객·상품 정답은 한 번만 센다. 낮은 평점이 purchase로 적재됐다고 자동으로 긍정 정답으로 삼지 않는다.
- `feedback >= 0.5`를 긍정으로 볼지, `feedback == 1.0`만 볼지는 유환과 확정한다. v0.1 함수는 이미 선택된 정답을 입력받으므로 둘 중 하나를 몰래 하드코딩하지 않는다.
- 정확도 지표는 정답이 없는 고객을 제외하고 제외 수를 보고한다. 정답이 있는데 추천이 없으면 0점이다. 이 둘을 혼동하지 않는다.
- 추천 상품 중복은 오류로 처리한다. 잘못된 목록을 자동으로 줄이거나 같은 적중을 두 번 계산하지 않는다.
- 서비스 ID는 DB item/user ID를 사용한다. 원본 데이터 ID는 `(source, source_id)` 또는 명확하게 source를 붙인 문자열로 구분한다. Amazon의 비연속 ID를 배열 행 번호로 쓰지 않는다.
- 미정의 값은 `None`/JSON `null`이며 화면은 ‘계산 불가’로 표시한다. 0은 계산했지만 성과가 없다는 뜻이다.
- JSON 실행의 고객 ID는 문자열로 통일한다. JSON 객체의 키는 문자열이므로 eligible_users에 정수를 섞으면 명령행 실행이 오류를 낸다. Python 함수 자체는 일관된 정수·복합 ID도 지원한다.
- 오프라인 지표 갱신은 평가 작업 완료 시다. 화면 30초 새로고침과 모델 재평가를 같은 뜻으로 쓰지 않는다. 30초는 화면 갱신 제안값이다.

## 2. 오프라인 지표 — 구현 완료

기호: Rᵤ는 고객 u의 중복 제거된 긍정 정답 집합, Lᵤ는 상위 K개 추천, hᵤⱼ는 j번째 추천이 정답이면 1, 아니면 0이다. 정확도 평균의 고객 집합 E는 제공된 eligible_users 중 |Rᵤ|>0인 고객이다.

| 지표·함수 | 공식 | 집계 단위·분모 | 갱신 |
|---|---|---|---|
| Recall@K / `ranking_metrics` | 고객별 |Lᵤ∩Rᵤ| / |Rᵤ|를 E에서 평균 | 고객별 동일 가중치; 정답 수가 많은 고객에 더 큰 가중치를 주지 않음 | 평가 완료 시 |
| NDCG@K / `ranking_metrics` | DCGᵤ=Σ hᵤⱼ/log₂(j+1), IDCGᵤ=Σⱼ₌₁…min(K,|Rᵤ|) 1/log₂(j+1); DCG/IDCG의 고객 평균 | E; 이진 관련도 | 평가 완료 시 |
| MAP@K / `ranking_metrics` | APᵤ=Σⱼ₌₁…K Precision@j×hᵤⱼ / min(K,|Rᵤ|); AP의 고객 평균 | E; 짧은 추천 목록이어도 분모를 반환 개수로 줄이지 않음 | 평가 완료 시 |
| 카탈로그 커버리지 / `catalog_coverage` | 고객들에게 추천된 서로 다른 상품 수 / 고정 평가 카탈로그의 서로 다른 상품 수 | 전체 제공 고객의 추천 목록; 빈 정답 고객도 포함. 카탈로그 밖 추천은 오류 | 평가 완료 시 |
| 목록 내 다양성 / `intralist_diversity` | 고객별 추천 상품 쌍의 평균 [1−cos(vᵢ,vⱼ)]를 고객별 평균 | 추천 2개 이상인 고객을 같은 가중치로 평균. 두 개 미만인 고객 제외 수 보고 | 평가 완료 시 |
| 브랜드 충성도(운영상: 최다 브랜드 비중) / `dominant_brand_share` | 고객별 maxᵦ nᵤᵦ / Σᵦ nᵤᵦ를 고객별 평균 | 구매·클릭·노출 각각 별도 계산. 브랜드를 아는 이벤트만 분모에 포함 | 오프라인 평가 완료 또는 명시된 이벤트 구간 집계 완료 |

### 커버리지·다양성의 주의점

- 커버리지는 0~1. 전체 고객 수·K·카탈로그 크기에 영향을 받으므로 같은 조건으로 비교한다. 상품이 많아 보이는 것 자체가 정확도 개선의 증거는 아니다.
- 다양성의 코사인 거리는 **0~2**다. 같은 방향은 0, 직교는 1, 반대 방향은 2다. 0~1로 표시하지 않는다.
- 비교하는 모델마다 다른 학습 상품 벡터를 사용하면 다양성의 기준 자체가 달라진다. 하나의 고정 콘텐츠 벡터 버전을 사용한다. 이미지 벡터라면 화면 이름도 ‘시각적 다양성’으로 표시한다.
- 코드가 입력 벡터를 정규화한다. 누락·0벡터·NaN·차원 불일치는 오류이며 해당 상품을 몰래 빼지 않는다.
- H&M 색상 변형은 v0.1에서 item 단위로 센다. product_code로 묶은 평가는 별도 이름·결과로 계산하고 뒤섞지 않는다.
- reference 다양성 구현은 정확성 우선의 Python 버전이며 큰 K·고객 수에 대한 속도 보장은 없다. 실제 전체 데이터 실행 전에 크기에 맞는 배치/벡터화가 필요할 수 있다.

### 브랜드 비중의 주의점

- 이 값은 브랜드 선호 성향의 대리 지표다. 추천 노출 구성이 행동을 제약할 수 있으므로 심리적 충성도로 단정하지 않는다.
- H&M 한 브랜드 안에서는 구조상 1이 될 수 있어 충성 고객의 증거가 아니다. 다중 브랜드 고객과 source별 결과를 구분한다.
- 없는 브랜드를 ‘기타’ 하나로 합치지 않는다. 브랜드 누락 이벤트 수·제외 고객 수를 함께 표시한다.
- 진짜 반복 구매는 여러 이벤트로 센다. 전송 재시도 중복 제거는 이벤트 적재 단계에서 처리한다.
- 브랜드 집중도는 높을수록 무조건 좋다는 정렬을 적용하지 않는다. 페르소나별 특성과 정확도·다양성의 균형을 함께 본다.

## 3. 서비스 화면 숫자 — 현재 API 또는 추가 구현 대상

아래는 아직 모두 구현됐다는 뜻이 아니다. ‘현재’와 ‘추가’를 구분해 표시한다.

| 숫자 | 계산·분모 | 집계 단위 | 갱신 제안 | 현재 상태 |
|---|---|---|---|---|
| 노출 수 | type=view 이벤트 수 | 실험·variant·기간 | 30초 조회 | 현재 API는 기간 필터 없는 누적 수 |
| 클릭 수 | type=click 이벤트 수 | 동일 | 30초 조회 | 현재 API는 원시 이벤트 수 |
| CTR | 클릭 수 / 노출 수 | 동일; 노출 0이면 운영 화면은 N/A 제안 | 30초 조회 | 현재 API는 노출 0일 때 0.0 반환; 의미 차이 합의 필요 |
| 노출 귀속 CTR(개선안) | 클릭된 고유 노출 수 / 고유 노출 수 | 실험·variant·기간 | 집계 완료 시 | impression_id·연결 규칙·중복 제거 필요. 현재 수치와 다른 이름/버전으로 관리 |
| 구매 수 | type=purchase 이벤트 수 | 동일 | 30초 조회 | 현재 누적 수 지원 |
| 구매 고객 전환율 | 구매한 고유 고객 / 실제 노출된 고유 고객 | 실험·variant·기간 | 집계 완료 시 | 추가 필요. purchase/view는 고객 전환율이 아님 |
| 고객 수 | 이벤트가 있는 고유 user_id 수 | 실험·variant | 30초 조회 | 현재 API는 이 정의이며 배정됐지만 미노출인 고객 수는 아님 |
| 지표 차이 | 후보−기준; 비율 지표는 필요시 %p 병기 | 같은 조건의 두 모델·그룹 | 평가/집계 완료 시 | 비교 처리 추가 |
| 상대 변화율 | (현재−기준)/기준×100% | 동일; 기준 0이면 계산 불가 | 집계 완료 시 | 추가 필요 |
| 신뢰구간 | 고객 단위 짝지은/그룹별 부트스트랩 등 고정 방법 | 오프라인은 고객, A/B는 배정 고객 단위 | 판정 작업 완료 시 | 아직 구현 안 됨 |
| p50·p95 지연 | 동일 범위 요청 시간의 50·95백분위 | 모델·실행환경·구간 | 벤치마크/관측 집계 완료 시 | 요청별 관측 수집 필요 |
| 유효·누락 고객 수 | 평가 계약의 포함·제외 건수 | 평가 작업 | 평가 완료 시 | 새 평가 모듈에서 반환 |
| 모델 수·활성 모델 | 레지스트리 행 수 및 status=active | 레지스트리 | 30초 조회 | 현재 GET /models로 가능 |
| 상품·브랜드·고객·이벤트 수 | 해당 테이블 건수, source별 별도 집계 | 데이터 버전/source | 적재 완료 또는 5분 조회 | 이벤트 type별 수 외에 추가 API 필요 |
| 데이터 누락률 | 누락 필드 행 수 / 해당 검사 대상 행 수 | 데이터 버전/source/필드 | 적재·품질 검사 완료 시 | 추가 필요 |
| 시뮬레이터 진행률 | 완료 세션 / 계획 세션 | run_id | 2초 조회 | run 관리 API 필요 |
| 알림 수·작업 수 | 상태별 알림/학습 작업 건수 | 지정 구간 | 30초 조회 | 추가 저장·API 필요 |

### 시뮬레이션 보고 기준 — 페르소나 v0.2

- 1차 파일럿은 브랜드 충성형·가격 민감형·탐색형·재구매형이다. 모델 비교는 동일 페르소나 안에서 인기 모델을 기준으로 한다. 원시 CTR의 페르소나 간 차이를 모델 개선 효과로 해석하지 않는다.
- 페르소나별 CTR 상승률 = (후보 CTR − 인기 모델 CTR) / 인기 모델 CTR × 100%. 절대 차이는 (후보 CTR − 기준 CTR) × 100 %p다. 기준 0이면 상승률은 null로 표시한다. 고객·노출 수와 source 구성을 함께 기록한다.
- 페르소나별 상승률 계산과 고객 단위 신뢰구간은 아직 구현하지 않았다. A/B에서 서로 다른 고객 그룹을 무조건 짝지은 표본으로 취급하지 않는다.
- 전체 점수는 고정된 페르소나 구성의 보조 요약으로만 사용한다. 동일 비중 4종이라면 각 1/4로 고정한다는 안이며, 일부 집단이 없을 때 임의로 비중을 다시 맞추지 않고 계산 불가를 표시한다.
- 인기도 특성은 source별 train 마지막 날 기준 7일 창과 source 내 정규화를 사용한다. 이는 시뮬레이터 입력 특성의 규약이며 Recall·MAP 공식 변경이 아니다.
- 강한 브랜드 충성형의 결과에는 ‘스트레스 테스트’ 표시를 붙인다. 신상품형은 날짜 정의를 확정하기 전까지 실행하지 않는다.

## 4. 결과 저장 규약

- 평가 JSON에는 definition_version, data_version, split, cohort, relevance_rule, vector_version, 모델 버전과 K를 남긴다. 모델 ID·작성 시각 등 실제 실행 정보는 호출자가 metadata로 넣는다. 예제 값을 실험 결과로 사용하지 않는다.
- 시뮬레이션 결과에는 persona_config_version, persona, run_id, seed, source 구성, 인기 기준 모델 버전, 예상가 비중도 보존한다.
- 각 지표마다 실제 분모를 보존한다. MetricSnapshot.n 하나만으로 고객 수·카탈로그 크기·누락 건수를 모두 표현할 수 없다. 평가 작업/metadata 저장 방식을 형우와 합의한다.
- `evaluate_report`는 정확도, 커버리지, 다양성, 브랜드 비중을 묶어 반환한다. 정확도와 목록 기반 지표의 평가 고객 분모는 다를 수 있으며 결과에서 확인 가능하다.
- 아직 DB 기록·API 업로드·부트스트랩·알림 판단·재학습은 구현하지 않았다. 계산 함수와 운영 로직을 분리해 정의를 공유한다.

## 5. 검증 예제

정답이 {A,B}, 추천이 [A,X,B]이고 K=3이면 Recall=1, AP=(1+2/3)/2=5/6이다. [A,B,X]로 순서가 좋아지면 Recall은 같지만 MAP·NDCG는 1이 된다. 테스트가 이 차이를 확인한다.

두 고객의 브랜드 비중이 각각 2/3과 1이면 평균은 5/6이다. 두 고객의 이벤트 수가 달라도 고객별 평균에 동일 가중치를 준다.

저장소 루트에서 실행:

```bash
python -m unittest discover -s recsys/tests -v
python -m recsys.evaluation recsys/examples/evaluation_toy.json
```

예제는 손으로 만든 가짜 데이터이며 실제 모델 점수가 아니다. 공유 데이터와 모델 가중치가 없어도 계산 정확성을 확인할 수 있다.
