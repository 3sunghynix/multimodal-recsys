# 광석 개발·발표 학습 기록

## 2026-10-29 — 평가 모듈부터 분리한 이유

### 우리가 해결한 문제

관리자 화면에 나오는 성능 숫자를 화면마다 다르게 계산하면 모델 비교를 믿을 수 없다. 그래서 먼저 DB나 화면과 독립적인 평가 함수를 만들고, 지표 정의서를 같은 공식으로 작성했다.

### 쉬운 설명

- Recall: 정답 상품 중 몇 개를 찾았는가.
- NDCG: 정답을 목록 위에 잘 올렸는가. 위쪽 적중에 더 큰 점수.
- MAP: 정답이 등장하는 위치의 정밀도를 평균해 추천 순서 전체를 평가.
- 커버리지: 전체 카탈로그 중 얼마나 많은 서로 다른 상품을 추천했는가.
- 다양성: 추천 상품끼리 콘텐츠 벡터가 얼마나 다른가.
- 최다 브랜드 비중: 고객 행동이 한 브랜드에 얼마나 집중되는가. 높을수록 무조건 좋은 점수는 아니다.

### 발표에서 반드시 구분할 것

1. 고객별 평균과 구매 건수 가중 평균은 다르다. 고객 A가 1개 중 1개, B가 3개 중 0개를 맞히면 고객별 Recall은 50%지만 구매 단위 적중률은 25%다.
2. 정답이 있는데 추천이 없으면 0점이다. 정답 자체가 없는 고객은 그 정확도를 정의할 수 없어 제외 수를 보고한다. 누락을 0으로 뭉개지 않는다.
3. 두 모델의 순위를 바꾸려면 같은 데이터·고객·카탈로그·K로 비교해야 한다. 데이터 버전이 다른 점수를 나란히 놓는 것은 공정한 비교가 아니다.
4. 브랜드 집중도가 높은 것이 충성도 개선이나 고객 만족을 증명하지 않는다. H&M만 있는 고객은 브랜드가 하나이므로 구조적으로 1이 될 수 있다.
5. 코사인 거리는 0~2다. 다양성을 0~1 지표라고 소개하지 않는다. 비교 모델마다 다른 벡터를 쓰면 평가 기준도 달라진다.
6. 손계산 예제·단위 테스트 통과와 실제 모델 성능 검증은 다르다. 이번 결과는 계산 코드의 정확성 확인이다.
7. 운영 경보와 통계적 A/B 승자 판정은 다르다. 10% 하락 경보 기준은 운영 가정이며 유의확률이 아니다.
8. 재학습 성공과 모델 채택도 다르다. 후보를 먼저 등록하고 평가·관리자 확인을 거친다.

### 직접 손으로 확인해 볼 예제

정답 {A,B}, 추천 [A,X,B], K=3:

- Recall = 2/2 = 1.
- 1번째 정답의 Precision = 1/1, 3번째 정답의 Precision = 2/3.
- AP = (1 + 2/3)/2 = 5/6.
- 정답을 [A,B,X]로 먼저 보여주면 Recall은 그대로이고 AP·NDCG는 좋아진다.

### 코드와 검증 범위

- `recsys/evaluation/metrics.py`: 계산 함수.
- `recsys/evaluation/__main__.py`: 준비된 JSON 입력을 평가하는 명령행 실행.
- `recsys/examples/evaluation_toy.json`: source가 겹치는 ID, 빈 정답 고객, 단순한 벡터를 포함한 가짜 예제.
- `recsys/tests/test_evaluation.py`: 손계산, 중복, 분모, 누락, source ID, 잘못된 벡터, 결과 덮어쓰기 방지 확인.

현재 구현하지 않은 것: 실제 parquet→입력 변환, feedback/split 필터, 공유 데이터 전체 모델 평가, DB 결과 저장, API 확장, A/B 신뢰구간, 알림 실행, 재학습, 대시보드 화면.

### 발표용 한 문단

“저는 관리자 화면의 요구사항과 평가 지표를 함께 설계했습니다. 모델마다 같은 고정 분할과 고객 집합을 사용하도록 평가 입력을 명시했고, 고객별 평균·정답 중복·추천 누락 처리를 코드와 정의서에서 통일했습니다. 손으로 답을 계산할 수 있는 예제와 예외 상황 테스트로 계산을 검증했습니다. 운영 경보·A/B 판정·재학습·교체는 별도의 정책으로 정리했으며, 실제 서비스 API 연동과 사용자 효과 검증은 다음 단계입니다.”

### 다음에 팀과 맞출 질문

- Amazon 3점(feedback +0.5)을 긍정 정답에 넣을지.
- 브랜드 집중도를 구매·클릭·노출 중 무엇을 주 지표로 보여줄지.
- 시각적 다양성의 콘텐츠 벡터 버전과 색상 변형 중복 기준.
- 지표 스냅샷 metadata·고객별 집계와 관리자 변경 이력을 어떻게 저장할지.

## 이번 검증 결과

- 독립 단위·CLI 테스트 22개 통과. 백엔드 전체 테스트나 PostgreSQL/Docker 실행 결과는 아님.
- 손계산 예제(K=3): Recall=0.5, NDCG≈0.459860, MAP≈0.416667, 커버리지=1, 다양성≈0.666667, 최다 브랜드 비중≈0.833333.
- 예제의 3명 중 정답이 없는 1명은 정확도 평균에서 제외되고, 정확도 평가 고객 수는 2명으로 보고됨.
- JSON의 정수 고객 ID와 문자열 키가 조용히 어긋나지 않도록 CLI 입력 형식도 검사함.


## 2026-10-29 — 페르소나 v0.2 리뷰를 관리자 설계에 반영

- 탐색형 CTR이 높은 이유가 모델이 아니라 기본 특성과 확률일 수 있다. 발표에서는 같은 페르소나 안에서 인기 모델 대비 변화를 보여준다.
- H&M과 Amazon은 관측 연도가 다르다. 최근 인기도는 source마다 자기 train 마지막 날 기준으로 계산해야 한쪽 데이터가 유리해지는 것을 줄일 수 있다.
- 브랜드 충성형은 강한 선호를 가진 가상 상황을 시험하는 설정이다. 실제 고객 분포를 재현했다고 말하지 않는다.
- 4종 파일럿으로 범위를 줄였지만 고객 생성·노출 연결·중복 방지 합의 전에는 실제 이벤트 전송을 시작하지 않는다.
- 설계 문서 v0.2와 평가 코드 v0.1은 별개다. 이번에는 보고 기준을 바꿨고 Recall·NDCG·MAP 공식은 바꾸지 않았다.
